## 변경 사항

### core-worker 0.2.4

#### 신규 플레이어 갱신 6~9.5초 → 1초 안팎 (#73)

- **증상**: 신규 플레이어 갱신 1건이 prod 로그 실측 기준 6~9.5초 걸렸다.
- **원인**: 갱신 1건이 약 1,100 row(브롤러 105 + 액세서리 5종 800 + 배틀 25 + 팀플레이어 210)를 만드는데, PK 가 IDENTITY 라 Hibernate 가 JDBC insert 배칭을 비활성화한다. 1,100 회 단건 INSERT 가 그대로 DB 왕복이 됐다.
- **수정**: 갱신 쓰기 경로 8개 테이블 PK 를 `V260707b`(통계 테이블)와 같은 패턴으로 **SEQUENCE(increment 100)** 로 전환해 배칭을 켰다. 로컬 실측 **709ms → 68ms**, DB 왕복 1,100회 → 21회.
- 테스트 공통 설정(`application-test-db.yml`)에 운영과 동일한 배칭 설정을 추가했다. 기존에는 테스트 클래스패스의 `application.yml` 이 메인 설정을 통째로 대체해 배칭이 테스트에서 빠져 있었다 (Hibernate Statistics 실측: insert 141건의 prepare 151 → 15).
- 갱신 완료 로그에 `elapsedMs` 를 추가해 개선 전후를 로그로 바로 비교할 수 있게 했다.
- 액세서리 5종의 저장 동작(신규는 전량 INSERT, 재갱신은 추가분만)을 고정하는 회귀 테스트를 추가했다. SEQUENCE 배치 INSERT 경로에서 이 필터가 깨지면 유니크 충돌로 갱신이 통째로 실패하기 때문이다.

#### 모드 ID 를 Long 으로 통일 (#74)

- 같은 값(브롤스타즈 모드 ID)을 담는 다른 컬럼은 모두 `bigint` 인데 `battle.event_mode_id` 만 `int` 라, `StatsBattleAggregateApplier` 가 `.toLong()` 으로 되돌리고 있었다.
- 외부 API 경계(`BattleBuilder`)에서 한 번만 변환하고 내부는 `Long` 으로 통일했다 — `BattleEvent.modeBrawlStarsId: Int? → Long?`, `.toLong()` 호출 2곳 제거.

### core-batch 0.4.1

#### 소유율 통계 카운트를 `OwnershipCountEmbedded` 로 추출 (#74)

- 소유율 통계 5개 엔티티(gear/gadget/star_power/hyper_charge/buffy)가 각각 들고 있던 `ownerCount` + `totalCount` 를 `@Embeddable` 로 묶었다. 5곳 모두 컬럼명이 같아 `@AttributeOverride` 없이 적용되며 **DDL 변경 없음**.
- `ownerCount <= totalCount` 불변식을 추가하니 `BrawlerItemOwnershipStatsAccumulator` 의 `totalCounts[key] ?: 0L` 폴백이 "소유 수는 0 초과인데 소유율은 0.0" 인 상태를 만들 수 있다는 게 드러났다. `add()` 가 아이템 카운트보다 총계를 먼저 올리므로 실제로는 도달 불가한 경로라 `error()` 로 교체했다.
- 불변식은 쓰기 경로에서만 검사된다 (`kotlin("plugin.jpa")`(noArg) 로 Hibernate 는 무인자 생성자 + 필드 주입으로 하이드레이션). 기존 데이터 조회는 안전하다.

### core-api 0.4.5

- 위 `OwnershipCountEmbedded` 추출에 맞춰 `BrawlerItemOwnershipStatisticsRepository` 의 카운트 접근 경로를 조정했다 (#74). **응답 스펙 변경 없음.**

### frontend 0.7.1

#### 컨텐츠가 짧은 페이지에서 푸터가 화면 중간에 뜨던 문제 (#72)

- `.app` 셸은 `min-height:100vh` + flex-column 이었지만 헤더와 푸터 사이 컨텐츠에 `flex:1` 을 주는 자식이 없어 남는 공간이 푸터 아래에 그대로 남았다. 홈·검색·about/terms/privacy 처럼 짧은 페이지에서 푸터가 화면 중간에 떴다.
- 페이지마다 루트 엘리먼트가 제각각이라(`<main>`, Fragment + `<div>`, `.main` 레거시) CSS 셀렉터로는 홈을 못 잡는다. 모든 페이지·loading·error 가 통과하는 root layout 한 지점에서 `{children}` 을 `flex-1` 래퍼로 감쌌다.
- Playwright 검증: `/` 푸터 bottom 707 → 900(뷰포트 하단), 모바일 375 폭 715 → 812. `/terms`, `/brawlers` 등 긴 페이지는 회귀 없음.

#### 갱신 실패 피드백 수정 (#73)

- **"갱신 실패" 문구가 절대 안 뜨던 버그**: `RenewalStatus` 와 `RenewalButton` 이 각자 `useMutation` 인스턴스를 만들어 버튼에서 낸 요청의 실패를 캡션 쪽이 볼 수 없었다. `mutationKey` + `useMutationState` 로 상태를 공유하도록 고쳤다.
- **백엔드가 FAILED 로 종결돼도 피드백이 없던 버그**: `RenewalStatus` 와 `NotFoundView` 에 `status === "FAILED"` 안내를 추가했다.
- 갱신 진행 중 폴링 주기를 1초 → 500ms 로 단축했다. `progressing` 중에만 발화하므로 평시 부하 변화는 없다.

> 갱신 진행 바(`RenewalProgress`)는 개발 중 추가했다가 이번 릴리즈에서 제거했다. 위 SEQUENCE 전환으로 대기 시간 자체가 사라졌고, 완료 애니메이션(300ms 채움 + 800ms 유지)이 실제 갱신보다 길어져 바가 깜빡이는 문제가 생겼기 때문이다. 진행 바가 값을 하는 구간은 10초 안팎이며, 그 아래는 기존 스피너 + "갱신 중…" 과 지연 시 "갱신이 지연되고 있어요" 문구로 충분하다. 이 때문에 frontend 는 minor 가 아니라 patch 로 나간다.

## 마이그레이션 필요 사항

**앱 배포 전 운영 DB 에 수동 선적용 필요 (2건). 이 프로젝트는 Flyway 미사용이다.**

적용 순서: `V260804a` → `V260804b`. 둘 다 멱등하게 작성돼 있다.

### 1. `V260804a__player_battle_identity_to_sequence.sql`

- 갱신 쓰기 경로 8개 테이블(player_brawler, 액세서리 5종, battle, battle_team_player)의 PK 를 IDENTITY → SEQUENCE(increment 100) 로 전환.
- `set default nextval` 을 함께 걸어 **IDENTITY 를 기대하는 구버전 앱과도 호환**된다 → DDL 선적용 후 앱 배포가 안전하다.
- `setval` 은 `max(id) + 100` 으로 초기화해 배포 전환 구간의 잔여 insert 와 충돌하지 않는다.
- 재적용 시 `setval` 만 +100 재상승(무해)하나, 신버전 앱이 캐시한 id 블록을 소진하기 전 재적용하면 극히 드물게 채번 충돌 여지가 있다 → **재적용은 갱신 처리 중이 아닐 때** 수행한다.
- 엔티티의 `@SequenceGenerator` 와 시퀀스 이름·increment 가 일치해야 한다.

### 2. `V260804b__battle_event_mode_id_to_bigint.sql`

- `battle.event_mode_id` 를 `int` → `bigint` 로 확장.
- ⚠️ **점검 시간대 적용 필수**: PostgreSQL 에서 int → bigint 는 저장 폭이 달라 **전체 테이블 재작성**이 필요하고, 그동안 `battle` 테이블에 ACCESS EXCLUSIVE 락이 걸린다 (읽기·쓰기 모두 차단). `battle` 은 이 스키마에서 가장 큰 테이블이다.
- 적용 전 소요 시간 가늠: `select count(*) from battle;`
- 무중단이 필요하면 이 방식 대신 신규 bigint 컬럼 추가 → 백필 → 스왑 절차를 쓴다.
- `information_schema` 확인 후 alter 하므로 이미 bigint 면 락도 잡지 않고 통과한다.
- 배포 순서: DDL 선적용 → 앱 배포. bigint 컬럼을 구버전 앱(Int 매핑)이 읽어도 실제 값이 int 범위 안이라 안전하다.

## 롤백 시 주의 사항

- **core-worker / core-api / core-batch**: 앱 이미지는 단순 롤백 가능. 위 마이그레이션 2건이 **구버전 앱과 호환되도록** 작성됐기 때문이다 (SEQUENCE 는 `default nextval` 로 IDENTITY 를 대체, bigint 는 int 범위 값만 담김).
- **DB 는 forward-only**: 마이그레이션 자체를 되돌리는 절차는 준비돼 있지 않다. 앱을 롤백해도 DB 는 그대로 두면 된다.
- **frontend**: Vercel 배포 롤백 가능. 롤백하면 갱신 실패 피드백이 다시 사라지지만 갱신 동작 자체는 정상이다.
