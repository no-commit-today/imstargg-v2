- 사전집계 테이블(`player_brawler_stats`) 조회 대신 battle 데이터에서 **실시간 계산 + Redis 캐시**로 전환.
- `PlayerBrawlerStatsRepositoryWithCache` 도입 — 캐시 히트 시 즉시 반환, 미스 시 battle 집계 쿼리로 계산 후 캐싱.
- 캐시 키에 `endBattleDate` 포함 — 조회 기간 경계가 키에 반영되도록 보정.
- `PlayerStatisticsQueryComposer` / `PlayerBrawlerStatsService` 를 새 Repository 구조에 맞춰 재구성.
- **외부 API(요청/응답) 형식 변경 없음** — 내부 데이터 소스만 사전집계 테이블 → on-the-fly + 캐시로 교체.

#### 기타

- graceful shutdown 설정 추가, `AsyncConfig` 조정.

## ⚠️ Breaking Changes

- **외부 API(요청/응답) 변경 없음.**
- **`player_brawler_stats` / `player_brawler_stats_item` 테이블 제거 (forward-only)**: core-api 의 플레이어 브롤러 통계가 더 이상 사전집계 테이블을 읽지 않고 battle 집계 + Redis 캐시에 의존. 구버전(0.2.x) 백엔드를 새 스키마에 배포하면 사라진 테이블을 참조하여 통계 조회 실패.
- **Redis 의존 신규 도입**: core-api / core-worker 가 플레이어 브롤러 통계 캐시에 Redis 를 사용 — Redis 가용성이 통계 조회 경로의 새 의존성.

## 마이그레이션 필요 사항

- **DB 마이그레이션** (db-core / Flyway):
  - `V260530__drop_player_brawler_stats_tables.sql` — `player_brawler_stats`, `player_brawler_stats_item` 사전집계 테이블 제거. **battle 데이터가 영구 보존되므로 데이터 손실 없음** (필요 시 on-the-fly 재계산).
- **Redis**: 플레이어 브롤러 통계 캐시를 신규 사용. core-api / core-worker 의 `application.yml` redis 연결 설정 확인 필요.
- **배포 순서**: db-core / redis-core 를 공유하는 backend 3개 앱(core-api / core-batch / core-worker) 은 신버전 동시 배포 권장. core-api ↔ core-worker 는 캐시 키/값 포맷을 공유하므로 함께 배포.

## 롤백 시 주의 사항

- **`V260530` 은 forward-only**. 롤백하여 0.2.x core-api(사전집계 테이블 조회)를 다시 배포하면 테이블이 없어 통계 조회가 실패한다. 코드 롤백이 필요하면 먼저 `player_brawler_stats` / `player_brawler_stats_item` 테이블을 재생성하고 재집계해야 한다.
- **core-api ↔ core-worker 동시 롤백 권장** — 두 앱이 브롤러 통계 캐시의 키/값 포맷을 공유하므로 한쪽만 롤백 시 캐시 미스매치 가능. 롤백 시 해당 캐시 flush 도 고려.
- frontend(GA4) / 인프라(도커·ECR) 변경은 단순 롤백 가능 — 특이사항 없음.
