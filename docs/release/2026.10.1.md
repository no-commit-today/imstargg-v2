## 변경 사항

### 통계 전투 수집량 10배 확대 (c08e0c63)

통계의 원천인 전투 수집 스케줄러가 초당 약 0.83회(운영 실측)만 브롤스타즈 API 를 호출해 통계 표본이 부족했다. 이를 초당 약 8.3회로 10배 늘린다.

### core-worker 0.3.0

- 플레이어마다 무작위 ID 를 따로 뽑는다. `stats_player` 는 같은 전투 참가자가 연속 ID 로 적재되어, 한 ID 에서 연속 N명을 읽으면 전투 로그가 겹쳐 battle_key 중복으로 걸러지고 수집량이 늘지 않았다.
- 한 틱의 플레이어를 전용 플랫폼 스레드 풀에서 동시에 조회한다. 순차 호출은 응답 지연(약 0.2초)에 묶여 초당 5회 남짓이 한계였다.
- 스케줄을 fixed-delay → fixed-rate 로 바꿨다. `app.schedule.stats-battle.interval` 이 틱 시작 간격이 되어 초당 호출 수 = `player-count / interval` 로 고정된다. 기본값 1s·1명 → **600ms·5명**.
- 동시에 점검(503) 응답을 받아도 점검 자동 등록은 틱당 한 번만 한다 (등록기의 조회 후 저장 경합으로 중복 등록되던 것을 방지).

### core-api 0.5.2 / core-batch 0.4.4

- 공통 모듈(`db-core`) `StatsPlayerJpaRepository` 변경(`findAllByIdGreaterThanEqual` 제거, `findFirstByIdGreaterThanEqualOrderByIdAsc` 추가)에 따른 버전 동기화. 두 앱은 해당 메서드를 쓰지 않아 **동작 변경 없음**.

### 앱 외 변경 (버전 무관)

- `brawlstars-client` README 추가 — 브롤스타즈 API 호출 한도(초당 약 50회), JVM 별 레이트리미터 구성, 앱별 실사용량을 정리했다.

## 배포 후 확인

- **429 응답**: 브롤스타즈 API 호출 한도는 초당 약 50회라 worker 의 초당 8.3회는 여유가 있다. 다만 JVM 레이트리미터(prod 초당 10회)의 약 83%를 써서, 같은 리미터를 쓰는 사용자 갱신이 잠깐 대기할 수 있다. 이 속도로 운영해 본 적은 없으므로 배포 후 몇 시간은 worker 로그에 `TooManyRequests` 가 없는지 확인한다.
- **적재량**: `stats_result_battle` 시간당 1,000~1,200건 → 1만~1.2만 건 근처면 의도대로다.
- **DB 커넥션**: worker 풀 5개·대기 제한 1.1초. `Connection is not available` 오류가 없는지 확인한다.
- **용량**: 원본 파티션은 10일 보존이라 약 0.34GB → 3.4GB 에서 멈춘다. 집계 테이블(enemy/pair)은 월 약 1.5GB → 최대 약 8GB 로 늘고 보존 기한이 없어 별도 보존 정책이 필요하다.
- **배치**: 통계 집계 잡은 현재 1~2분 → 10~20분 예상. 잡 간격(1시간) 안이다.

## 롤백 시 주의 사항

앱 이미지 단순 롤백 가능. 데이터 정리도 필요 없다.

- **core-worker**: 롤백하면 이전 수집 속도(초당 약 0.83회)로 돌아간다. 이미 쌓인 원본 전투는 10일 보존으로 자연 삭제되고, 집계는 다음 배치에서 그대로 재계산된다. 속도만 낮추려면 롤백 대신 `player-count`·`interval` 을 조정해 재배포해도 된다.
- **core-api / core-batch**: 동작 변경이 없어 롤백 영향 없음.
