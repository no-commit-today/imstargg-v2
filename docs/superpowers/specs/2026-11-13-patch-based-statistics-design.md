# 패치 기준 통계 집계와 최근 업데이트 일시 설계

- 작성일: 2026-11-13
- 대상: `core/core-batch`(집계 잡), `infrastructure/db-core`(엔티티·DDL), `core/core-enum`(통계 유형, 기간 옵션 삭제), `core/core-api`, `imstargg-frontend`, `imstargg-deploy`(CronJob)
- 상태: 검토 중 (구현 전)
- 관련: 통계를 날짜 기준에서 패치 기준으로 바꾸는 재설계의 두 번째 스펙이다. 첫 번째 스펙(`2026-11-11-brawlstars-news-collect-patch-date-design.md`)이 만드는 패치일 목록을 읽는다.
- 기준 코드: `develop`(2026-11-13, `edd949dd`). 조합 통계 재설계(상대·2인 조합의 키에서 이벤트 제거, 3인 조합 추가, 주 단위 버킷)가 들어간 상태다.

## 1. 배경

지금 통계는 날짜로 끊는다. 1인 통계는 일 단위로, 상대·조합 통계는 주 단위로 쌓고, 조회할 때 기간 옵션 8종(이번 주, 지난 주부터 등)으로 합산한다. 집계 잡은 하루에 한 번 돈다.

- **패치 전후가 섞인다.** 밸런스 패치가 주 중간에 있으면 한 기간 안에 패치 전과 후의 전투가 함께 들어간다.
- **하루에 한 번만 바뀐다.** 화면에는 통계가 언제 것인지 표시가 없다.
- **늦게 들어온 전투를 놓친다.** 적재는 7일 전 전투까지 받는데, 1인 통계 잡은 다음 날 03:00 에 전날 하루치를 한 번 읽고 끝난다. 그 시점에 읽는 전투는 77만–90만 건이고, 그 날짜의 원본은 결국 약 200만 건이 된다.

2026-11-12, 13 운영 DB 에서 읽기 전용으로 확인한 사실이다.

- **통계가 건드리는 줄 수**: 최근 전투 22만 5천 건(약 3시간치)이 건드리는 키는 1인 승률 18,215, 상대 49,146, 2인 조합 22,189, 3인 조합 124,533 이다.
- **키 공간의 상한**(브롤러 111 × 티어 구간 6): 상대 73,260, 2인 조합 36,630, 3인 조합 1,330,890. 집계 중 메모리는 이 상한으로 묶인다.
- **여러 날짜를 id 순으로 읽기**: `battle_date between … and id > … order by id limit 1000` 은 파티션 10개에서 실행 6.1ms, 계획 25.5ms 다. 날짜가 하나면 실행 1.6ms 다.
- **상한 id 쿼리**: 최근 8일에서 "10분 전까지 저장된 행의 가장 큰 id"는 48.7ms 다.
- **처리 속도**: 1인 승률 잡은 읽기와 쓰기를 합쳐 약 80만 건을 2분에 처리한다. 상대·조합은 재지 않았다.
- **테스트 DB**: H2(`MODE=PostgreSQL`)는 `insert … on conflict do update` 를 문법 오류로 거부한다. `update` 는 없는 키에 0건을 돌려준다.

## 2. 범위

### 만드는 것

- **패치별 통계 테이블 5개**: 1인 승률, 1인 순위, 상대, 2인 조합, 3인 조합. 키마다 한 줄에 누적한다.
- **체크포인트**: 통계 유형 × 패치마다 한 줄. 어디까지 읽었는지, 어떤 날짜 범위로 만든 숫자인지, 반영된 가장 최근 전투 일시를 적는다.
- **집계 잡 5종**: 통계 유형마다 하나. 3시간마다 돌며 새로 들어온 전투만 더하고, 패치 목록이 바뀌면 범위를 맞춘다.
- **API**: 패치 목록 엔드포인트. 통계 엔드포인트는 기간 대신 패치일을 받는다.
- **화면**: 기간 선택을 패치 선택으로 바꾸고 "최근 업데이트"를 보인다.

### 없애는 것

- 기간 옵션 8종과 기간 파라미터
- 일별 통계 엔드포인트와 브롤러 상세의 일별 추이 차트
- 옛 통계 테이블 5개, 옛 집계 잡 5종, 조합 테이블용 월 파티션 관리

### 범위 밖

- 패치일 등록과 뉴스 수집 (첫 번째 스펙)
- 소유 통계, 플레이어별 통계
- 원본 전투 테이블과 그 인덱스 (그대로 둔다)
- 잡 실패를 알려 주는 감시 장치

## 3. 결정 요약

| 항목 | 결정 |
|---|---|
| 통계 단위 | 패치마다 키별 한 줄에 누적한다. 날짜·주 단위 줄은 두지 않는다. |
| 패치 가리키기 | 패치 줄의 id 로 가리킨다. 화면과 API 는 패치일로 부른다. |
| 테이블 이름 | 새 통계 테이블은 지금 통계 테이블의 이름을 그대로 쓴다. 채우는 동안에는 `_new` 를 붙여 두고, 전환 때 옛 테이블을 `_backup` 으로 바꾸면서 이름을 넘겨받는다. |
| 어느 패치에 넣나 | 전투의 날짜가 정한다. 패치일 다음 날부터 다음 패치일 전날까지가 그 패치의 범위다. 패치 당일의 전투는 집계하지 않는다. |
| 집계 방식 | 원본 전투의 id 를 체크포인트로 삼아 새로 들어온 전투만 더한다. |
| 실행 주기 | 3시간마다. 통계 유형마다 크론잡 하나, 10분씩 엇갈린다. 파라미터는 없다. |
| 체크포인트 | 통계 유형 × 패치마다 한 줄 |
| 패치 목록이 바뀌면 | 줄에 적어 둔 "적용한 날짜 범위"와 지금의 범위를 견줘, 빠진 날은 다시 읽어 빼고 새로 든 날은 다시 읽어 더한다. 집계 잡 안에서 한다. |
| 쓰기 | 키로 갱신하고 없던 키만 넣는 두 단계. H2 와 PostgreSQL 에서 같은 SQL 로 돈다. |
| 겹친 실행 | 체크포인트 줄의 수정 번호가 읽었을 때와 같을 때만 쓴다. |
| 최근 업데이트 | 체크포인트에 적은 "반영된 가장 최근 전투 일시". 화면에는 다섯 유형 중 가장 이른 값을 보인다. |
| 화면의 패치 | 통계가 있는 패치 중 최근 3개. 기본은 가장 최근 패치. |
| 지난 패치의 통계 | 지우지 않는다. |
| 일별 추이 차트 | 없앤다. |
| 전환 | 옛 통계 옆에서 새 통계를 먼저 채우고, API 와 화면을 한 번에 바꾼다. 호환 구간은 두지 않는다. |
| 옛 통계 | 전환 때 `_backup` 테이블로 이름을 바꿔 1주 두었다가 지운다. 따로 덤프하지는 않는다. |

## 4. 데이터 모델

엔티티는 db-core 에 두고 DDL 은 `schema.sql` 과 마이그레이션 파일 양쪽에 멱등하게 쓴다. 외래 키 제약과 파티션은 두지 않는다. 컬럼 이름은 기존 통계 테이블을 따르고, 아래에는 달라지는 것만 적는다.

### 4.1 통계 테이블

| 통계 | 테이블 | 한 줄의 키 | 값 |
|---|---|---|---|
| 1인 승률 | `brawler_battle_result_stats` | 패치 · 티어 구간 · 이벤트 · 브롤러 | 승·패·무·합, 스타플레이어 수 |
| 1인 순위 | `brawler_battle_rank_stats` | 패치 · 티어 구간 · 이벤트 · 브롤러 | 순위별 횟수 10개, 합 |
| 상대 | `brawler_enemy_battle_result_stats` | 패치 · 티어 구간 · 브롤러 · 상대 브롤러 | 승·패·무·합 |
| 2인 조합 | `brawler_pair_battle_result_stats` | 패치 · 티어 구간 · 브롤러 둘 | 승·패·무·합 |
| 3인 조합 | `brawler_trio_battle_result_stats` | 패치 · 티어 구간 · 브롤러 셋 | 승·패·무·합 |

- **이름**: 표의 이름은 전환 뒤의 이름이고, 지금 통계 테이블의 이름과 같다. 옛 테이블 옆에서 채우는 동안에는 `_new` 를 붙인 이름(`brawler_battle_result_stats_new` 등)을 쓰고, 전환 때 이름을 바꾼다(10장). 인덱스와 제약의 이름도 테이블 이름을 따라 함께 바꾼다.
- **패치 컬럼**: `brawlstars_patch_id`. 옛 테이블의 날짜 컬럼(`battle_date`, `start_battle_date`, `end_battle_date`) 자리에 들어간다.
- **유니크**: 표의 키 순서 그대로 한 개. 같은 키의 줄이 둘 생기지 않게 막는다. 겹친 실행의 이중 덧셈은 막지 못하고, 그것은 체크포인트의 수정 번호가 막는다(5.6).
- **인덱스**: 남는 조회는 모두 유니크 키의 앞부분으로 찾는다. 조합은 브롤러가 어느 자리에 있든 찾아야 해서, 2인 조합에 (패치, 티어 구간, 둘째 브롤러) 한 개, 3인 조합에 둘째·셋째 브롤러로 두 개를 더한다.
- **1인 순위의 값**: `rank1_count` 부터 `rank10_count` 까지 컬럼 10개다. 지금은 JSON 배열인데, 두 단계 쓰기에서는 배열의 칸별 덧셈을 쓸 수 없다.
- **조합의 브롤러 순서**: 지금처럼 브롤러 id 오름차순으로 넣는다.
- **id**: 자동 증가(identity). 이 테이블들은 잡이 SQL 로 직접 쓴다.
- **크기**: 가장 큰 3인 조합도 패치 하나에 최대 133만 줄이다.

### 4.2 체크포인트 `stats_checkpoint`

한 줄이 통계 유형 × 패치다.

| 컬럼 | 타입 | 내용 |
|---|---|---|
| `stats_checkpoint_id` | bigint, identity PK | |
| `stats_type` | varchar, not null | 통계 유형 5종 |
| `brawlstars_patch_id` | bigint, not null | 패치 줄의 id |
| `last_read_battle_id` | bigint, not null | 체크포인트. 원본 전투를 이 id 까지 읽어 이 패치 통계에 반영했다. |
| `applied_start_date` | date, not null | 이 숫자를 만들 때 쓴 범위의 첫 날 |
| `applied_end_date` | date, null | 범위의 마지막 날. 다음 패치가 없으면 비운다(끝 없음). |
| `last_battle_at` | timestamptz, null | 반영된 가장 최근 전투 일시. 화면의 "최근 업데이트"다. 반영된 전투가 없으면 비어 있다. |
| `version` | bigint, not null | 수정 번호. 쓸 때마다 1 올린다. |
| `created_at`, `updated_at` | timestamptz | 공통 컬럼 |

- 유니크는 (`stats_type`, `brawlstars_patch_id`) 다.
- 1인 순위의 체크포인트는 순위형 원본의 id 이고, 나머지 넷은 결과형 원본의 id 다.

**지키는 규칙은 하나다.** 한 패치의 통계는 "전투 날짜가 적용한 범위 안이고 id 가 체크포인트 이하"인 원본 전투를 집계한 값과 같다. 모든 쓰기 트랜잭션이 통계 줄과 체크포인트 줄을 함께 바꾸므로, 잡이 어디서 죽어도 이 규칙이 성립하고 다음 실행이 이어서 한다.

### 4.3 원본 보관과 등록 기한

범위 맞추기는 원본 전투를 다시 읽는다. 패치일은 오늘에서 30일 안에서만 등록·수정·삭제되므로(첫 번째 스펙), 다시 읽는 날짜는 모두 최근 30일 안이다. 원본 보관 일수(45)가 등록 기한(30)보다 길어야 하고, 이 관계를 단위 테스트로 고정한다.

## 5. 집계 잡

### 5.1 실행

잡은 통계 유형마다 하나이고 CronJob 도 하나씩이다. 3시간마다 돌고 10분씩 엇갈린다.

| 통계 유형 | 스케줄(UTC) | KST |
|---|---|---|
| 1인 승률 | `0 */3 * * *` | 00:00, 03:00, … |
| 1인 순위 | `10 */3 * * *` | 00:10, 03:10, … |
| 상대 | `20 */3 * * *` | 00:20, 03:20, … |
| 2인 조합 | `30 */3 * * *` | 00:30, 03:30, … |
| 3인 조합 | `40 */3 * * *` | 00:40, 03:40, … |

- 파라미터는 없다. 무엇을 읽을지는 체크포인트와 패치 목록이 정한다.
- 같은 유형의 실행은 CronJob 설정으로 겹치지 않는다. 겹치더라도 수정 번호 확인이 막는다.
- 집계 규칙(티어 구간 판정, 봇 전투 제외, 조합의 브롤러 순서)은 지금의 집계 그대로다. 키에서 날짜가 빠지고 패치가 들어갈 뿐이다.

### 5.2 패치의 범위

- 한 패치의 범위는 패치일 다음 날부터 다음 패치일 전날까지다. 다음 패치가 없으면 끝이 없다.
- 패치 당일의 전투는 어느 패치에도 넣지 않는다. 점검 시각을 알 수 없기 때문이다.
- 가장 이른 패치보다 앞선 날짜의 전투는 집계하지 않는다.
- 패치일이 연이은 날짜면 앞 패치의 범위는 비어 있다.

패치일이 11-03, 11-11 이면 11-03 패치의 범위는 4일부터 10일까지이고, 11-11 패치의 범위는 12일부터 끝 없음이다.

### 5.3 한 번의 실행

1. **상한 id 를 잡는다.** 실행 시작 10분 전까지 저장된 원본 중 가장 큰 id 다. 한 실행 내내 같은 값을 쓴다. 10분은 저장 중인 트랜잭션이 끝나기를 기다리는 여유다.
2. **지금의 범위를 계산한다.** 패치 목록을 읽어 패치마다 범위를 구한다.
3. **삭제된 패치를 정리한다.** 체크포인트 줄은 있는데 패치가 없으면, 그 패치의 통계 줄과 체크포인트 줄을 지운다. 운영자가 어드민에서 삭제한 패치만 해당한다. 통계 줄은 티어 구간별로 나눠 지운다.
4. **범위를 맞춘다.** 적용한 범위가 지금의 범위와 다른 줄을 하루씩 옮긴다(5.4).
5. **평소대로 읽는다.** 체크포인트 뒤의 새 전투를 더한다(5.5).

### 5.4 범위 맞추기

체크포인트 줄의 적용한 범위가 지금의 범위와 다르면 하루씩 옮긴다. 트랜잭션 하나가 하루다.

- **빠진 날**: 그 날짜의 전투 중 id 가 체크포인트 이하인 것을 다시 읽어 뺀다. 같은 트랜잭션에서 적용한 범위를 하루 줄인다.
- **새로 든 날**: 그 날짜의 전투 중 id 가 체크포인트 이하인 것을 다시 읽어 더한다. 같은 트랜잭션에서 적용한 범위를 하루 넓힌다.
- **순서**: 줄일 때는 범위의 바깥쪽 날부터, 늘릴 때는 범위에 붙은 날부터 한다. 적용한 범위가 늘 이어진 한 구간으로 남는다. 줄이기를 먼저 하고 늘리기를 한다.
- **끝이 없던 줄을 줄일 때**: 바깥쪽 날은 오늘(KST)이다.
- **범위가 다 비면**: 마지막 날을 빼는 트랜잭션에서 체크포인트 줄도 지운다. 나중에 범위가 다시 생기면 새 패치처럼 처음부터 읽는다.
- **최근 전투 일시**: 끝을 줄이면 새 끝 날짜의 마지막 시각을 넘지 않게 내린다. 더하면 더한 전투의 가장 늦은 시각과 견줘 큰 값을 둔다.
- **맞추기가 끝나지 않은 패치는 평소 읽기를 하지 않는다.** 섞으면 새로 든 날의 전투를 두 번 더할 수 있다.

다시 읽는 날짜는 모두 최근 30일 안이라 원본이 남아 있다(4.3).

### 5.5 평소 읽기

대상은 적용한 범위가 지금의 범위와 같은 패치다.

- **줄 만들기**: 체크포인트 줄이 없는 패치는 줄을 만든다(체크포인트 0, 적용한 범위는 지금의 범위). 두 경우에는 만들지 않는다.
  - 범위에 오늘(KST)까지의 날짜가 하나도 없을 때. 패치일이 오늘이거나 패치일이 연이은 경우다.
  - 범위의 첫 날이 원본에 남아 있는 가장 이른 날짜보다 이를 때. 앞부분이 빠진 통계가 온전한 것처럼 보이지 않게 한다.
- **읽기**: 원본에서 "전투 날짜가 줄의 적용한 범위 안이고, id 가 체크포인트보다 크고 상한 이하"인 전투를 id 순으로 읽는다. 지금 통계 잡과 같은 키셋 방식이고 한 번에 5,000건씩 읽는다.
- **저장**: 전투 10만 건을 읽을 때마다 저장하고 체크포인트를 마지막으로 읽은 id 로 올린다. 10만은 초기값이고, 가동 뒤 재 보고 고친다.
- **끝**: 다 읽으면 체크포인트를 상한 id 로 올린다. 새 전투가 없었어도 올린다.

한 실행은 원본에 범위가 남아 있는 모든 패치를 읽는다. 11월 12일 실행은 11-03 패치(4–10일)와 11-11 패치(12일부터)를 둘 다 읽는다. 그래서 늦게 들어온 10일 전투가 11-03 패치에 들어간다. 범위가 끝난 지 오래된 패치는 새 전투가 없어 읽기가 바로 끝난다.

### 5.6 쓰기 트랜잭션

원본 읽기와 집계는 트랜잭션 밖에서 메모리에 모으고, 트랜잭션은 쓰기만 한다.

1. **첫 문장은 체크포인트 줄이다.** 수정 번호가 읽었을 때와 같을 때만 줄을 고치고 번호를 1 올린다. 고쳐진 줄이 하나가 아니면 다른 실행이 먼저 쓴 것이므로 트랜잭션을 실패시킨다. 통계 줄을 건드리기 전에 여기서 멈춘다.
2. **더하기**: 키로 갱신한다. 갱신된 줄이 없는 키만 새로 넣는다.
3. **빼기**: 뺄 수 있을 때만 갱신되도록 조건을 걸고 키로 갱신한다. 갱신된 줄이 없으면(뺄 줄이 없거나 빼면 음수가 됨) 트랜잭션을 실패시킨다. 합이 0 이 된 줄은 지운다.

빼기가 맞으려면 세 가지가 성립해야 한다.

- 원본 전투는 추가만 된다(저장된 행을 고치거나 지우지 않는다. 날짜 파티션 삭제는 예외다).
- 상한 id 아래로 뒤늦게 끼어드는 전투가 없다.
- 더할 때와 뺄 때의 집계 규칙이 같다. 집계 규칙을 바꾸는 배포는 통계를 비우고 다시 채우는 것과 함께 해야 한다(8장).

### 5.7 첫 실행

따로 만든 잡이 아니라 평소 잡이다. 체크포인트 줄이 없으니 패치마다 줄을 만들고 범위의 원본을 처음부터 읽는다.

- 10만 건마다 저장하므로 중간에 죽거나 시간 제한에 걸려도 다음 실행이 이어서 한다.
- 양은 원본에 남은 날짜 전부다. 27일치면 유형당 약 5,400만 건이고, 1인 승률의 속도로 약 2시간 15분이다.
- 다섯 유형이 함께 채우는 동안의 DB 부하는 재지 않았다. 이 단계에서는 화면이 새 테이블을 읽지 않으므로, 부하가 크면 CronJob 을 멈췄다가 하나씩 켠다. 멈춘 잡은 체크포인트에서 이어 간다.

### 5.8 장면

| 일어난 일 | 11-03 패치 줄 | 11-11 패치 줄 |
|---|---|---|
| 11-11 21:20 에 11-11 패치를 등록 | 11일 전투를 빼서 4–10일로 줄인다. 그 뒤 4–10일의 늦게 들어온 전투를 읽는다. | 새로 만들어 12일부터 읽는다. |
| 11-11 패치를 삭제 | 11일부터 오늘까지 하루씩 더해 끝 없음으로 넓힌다. | 통계와 줄을 지운다. |
| 11-11 을 11-12 로 수정 | 11일을 더해 4–11일로 넓힌다. | 12일을 빼서 13일부터로 줄인다. |
| 11-07 을 뒤늦게 끼워 넣음 | 10, 9, 8, 7일을 하루씩 빼서 4–6일로 줄인다. | 변화 없음 |

- 마지막 줄에서 11-07 패치는 줄을 새로 만들어 8–10일을 처음부터 읽는다.
- 첫 줄이 평소의 경로다. 패치는 늘 일어난 뒤에 등록되므로, 패치를 등록할 때마다 다섯 유형이 모두 하루치 이상을 다시 읽어 뺀다.

## 6. API (core-api)

| 메서드·경로 | 내용 |
|---|---|
| `GET /v1/statistics/patches` | 새로 추가. 선택할 수 있는 패치를 최신순으로 최대 3개 준다. 항목은 패치일(`patchDate`)과 최근 업데이트 일시(`lastBattleAt`)다. |
| 통계 7개 (`/v1/statistics/brawler/result`, `/brawler/rank`, `/brawler/enemy/result`, `/brawler/pair/result`, `/brawler/trio/result`, `/pair/result`, `/trio/result`) | `dateRange` 를 없애고 `patchDate`(`yyyy-MM-dd`, 필수)를 받는다. 응답 모양은 그대로다. |
| `GET /v1/statistics/brawler/result/daily` | 삭제 |
| `GET /v1/statistics/brawler/item/ownership` | 그대로 |

- **선택할 수 있는 패치**: 다섯 통계 유형 모두에 반영된 전투가 있는 패치다(체크포인트 줄의 최근 전투 일시가 다섯 줄 모두 있음).
- **최근 업데이트 일시**: 다섯 유형의 최근 전투 일시 중 가장 이른 값이다. 모든 통계가 적어도 그 시각까지 반영됐다는 뜻이다.
- **패치일 검증**: 선택할 수 있는 패치면 목록의 3개 밖이어도 받는다. 아니면 404 다. "최근 3개"는 목록에만 적용해, 목록이 넘어가는 순간에 보고 있던 화면이 깨지지 않게 한다.
- **기본값**: 두지 않는다. 화면이 목록의 첫 항목으로 정한다.
- **기간 파라미터**: 받지 않는다. 옛 화면을 위한 호환 경로를 두지 않는다(10장).
- **숫자 규칙**: 분모, 표본 하한, 티어 점수, 상위 N 은 그대로다. 합산 범위만 기간에서 패치 하나로 바뀐다. 키마다 한 줄이라 조회할 때 날짜·주 단위로 합산하던 것이 없어진다.
- **캐시**: 통계 캐시 키의 시작·끝 날짜를 패치로 바꾸고 키 접두사 버전을 올린다. 30분은 그대로다. 패치 목록도 같은 캐시에 둔다.

최근 업데이트를 통계 응답마다 넣지 않고 패치 목록에 두는 이유는 셋이다. 통계 응답 7개 중 6개가 맨 목록이라 넣으려면 응답 모양을 모두 바꿔야 한다. 한 화면이 여러 통계 유형을 함께 보인다. 패치 선택 상자가 어차피 패치 목록을 부른다.

## 7. 화면 (imstargg-frontend)

대상은 `/brawlers`, `/brawlers/[id]`, `/events/[id]` 다.

| 항목 | 내용 |
|---|---|
| 패치 선택 | 기간 선택 자리에 둔다. 최대 3개, 표시는 "11월 11일 패치". |
| 주소 | `?patch=2026-11-11`. 가장 최근 패치면 생략한다. 옛 `?date=` 와 목록에 없는 값은 가장 최근 패치로 본다. |
| 최근 업데이트 | 패치 선택 옆에 "최근 업데이트: 55분 전". 플레이어 화면과 같은 문구와 상대 시간이다. |
| 일별 추이 차트 | `/brawlers/[id]` 에서 지우고, 쓰는 곳이 없어지는 차트 라이브러리도 뺀다. |
| 미리 받아 두는 기본 통계 | 서버가 패치 목록과 통계를 같은 렌더에서 받아 함께 내려 준다. 화면은 그 목록으로 기본 패치를 정한다. 표시와 숫자의 패치가 어긋나지 않는다. |
| 목록이 비었거나 못 받았을 때 | "통계를 준비하고 있습니다"를 보인다. 렌더와 빌드가 실패하지 않아야 한다. 지금은 통계 조회가 실패하면 페이지 렌더가 실패한다. |

기간 옵션 8종과 그 표시, 기본 기간 상수는 지운다.

## 8. 오류 처리와 복구

- **예외는 그대로 던진다.** 잡이 그 자리에서 실패하고, 다음 실행이 체크포인트에서 이어 간다. 끝난 트랜잭션은 남는다.
- **겹친 실행**: 수정 번호가 맞지 않는 쪽이 실패한다. 통계는 그대로다.
- **뺄 수 없는 빼기**: 실패시킨다. 통계와 원본이 어긋났다는 뜻이라 조용히 넘기지 않는다. 같은 자리에서 계속 실패하면 그 유형의 그 패치가 멈추고 화면의 최근 업데이트도 멈춘다.
- **다시 채우기**: 어긋난 (통계 유형, 패치)의 통계 줄과 체크포인트 줄을 지우면 다음 실행이 원본에서 다시 채운다. 범위의 첫 날이 원본에 남아 있는 패치만 가능하다.
- **집계 규칙을 바꿀 때**: 다섯 유형의 통계 줄과 체크포인트 줄을 지우고 다시 채운다. 원본에 남은 날짜만큼만 돌아온다.

## 10. 배포

### 선행 조건

- 첫 번째 스펙이 운영에 있다(패치 테이블과 초기 패치일).
- `develop` 의 조합 통계 재설계가 운영에 있다. 아래의 옛 테이블과 옛 잡은 그 상태를 가리킨다.
- 운영의 원본 보관이 45일이다.

### 1단계: 채우기

1. 운영 DB 에 마이그레이션 SQL 을 직접 적용한다(`_new` 를 붙인 통계 테이블 5개, 체크포인트 테이블). 새 테이블뿐이라 떠 있는 앱에 영향이 없다.
2. core-batch 를 배포한다.
3. 그 뒤에 배포 설정에 새 CronJob 5개를 추가한다. 먼저 추가하면 옛 이미지가 모르는 잡 이름으로 뜬다.

옛 잡, 옛 테이블, API, 화면은 그대로다. 사용자에게 보이는 변화가 없다.

### 전환으로 넘어가는 조건

1. **체크포인트 줄**: 통계 유형 5 × 줄이 만들어진 패치 수만큼 있고, 적용한 범위가 패치 목록과 같고, 체크포인트가 실행마다 오른다.
2. **옛 통계와 비교(1인 승률·1인 순위)**: 줄이 만들어진 가장 오래된 패치로 견준다. 새 값이 옛 값 이상이고, 그 비율이 원본 건수의 비율로 설명되고, 브롤러별 승률이 비슷해야 한다. 옛 잡이 늦게 들어온 전투를 놓치므로 새 합은 옛 합의 두 배 안팎이 정상이다.
3. **시험 패치를 넣었다 빼기**: 범위가 끝난 패치 안에 시험 패치를 등록했다가 지운다. 지운 뒤 그 패치의 숫자가 등록 전과 정확히 같아야 한다. 날짜는 8일 넘게 지나 늦게 들어올 전투가 없고 등록 기한 30일 안이어야 한다. 하루치 빼기와 더하기를 운영 데이터로 미리 돌려 보는 절차이고, 3인 조합 하루치의 쓰기 시간도 여기서 잰다.
4. **상대·조합**: 옛 테이블이 주 단위라 직접 견주지 못한다. 표본 규모와 상위 조합이 비슷한지 눈으로 확인한다.

### 2단계: 전환

core-api, 프론트, core-batch 를 한 릴리스로 내보낸다. 이 릴리스의 코드는 통계 테이블을 `_new` 없는 이름으로 읽고 쓴다.

1. **배포 설정에서 통계 CronJob 을 모두 뺀다.** 옛 5개와 새 5개다. 돌고 있는 잡이 끝나기를 기다린다. 새 잡은 이름을 바꾸는 동안 쓰지 않아야 하고, 멈춘 사이의 전투는 다시 켠 뒤 체크포인트에서 이어 읽는다. 여기까지는 화면에 보이는 변화가 없다.
2. **프론트를 올린다.** 새 프론트는 패치 목록을 못 받는 동안 "통계를 준비하고 있습니다"를 보인다.
3. **이름을 바꾸는 SQL 을 적용한다.** 옛 통계 테이블 5개에 `_backup` 을 붙이고, `_new` 테이블 5개에서 `_new` 를 뗀다. 인덱스와 제약의 이름도 함께 바꾼다. 한 트랜잭션으로, 락 대기 시간을 짧게 걸어 적용한다.
4. **core-api 와 core-batch 를 배포한다.**
5. **배포 설정에 새 CronJob 5개를 다시 추가한다.**

- **함께 지우는 것**: 옛 조회 코드, 일별 통계 엔드포인트, 기간 옵션, 옛 잡 5종, 조합 테이블용 월 파티션 관리.
- **끊기는 구간**: 2번부터 4번이 끝날 때까지, 곧 프론트 배포에서 core-api 배포가 끝날 때까지 통계 영역이 준비 중으로 보인다. 3번과 4번 사이에는 옛 core-api 가 구조가 바뀐 테이블을 읽어 실패하지만, 새 프론트는 그동안 통계를 요청하지 않는다. 프론트를 나중에 올리면 그 사이 옛 화면이 오류로 보인다.
- **적용 시간대**: 트래픽이 적고 배치 시간대(02:00–09:00 KST)를 벗어난 때에 한다. 3번과 4번 사이에 옛 core-batch 의 파티션 관리 잡(02:00 KST)이 돌면, 조합 통계 테이블을 원래 이름으로 찾아 월 파티션을 만들려다 실패한다.
- **옛 잡이 멈춘다.** `_backup` 테이블은 그날부터 갱신되지 않는 사본이 된다.
- **`_backup` 이라는 이름**: 조합 재설계 때 쓴 `_legacy` 테이블이 아직 남아 있어도 이름이 겹치지 않는다.

### 3단계: 옛 테이블 삭제

`_backup` 테이블 5개와 월 파티션 함수를 지우는 SQL 을 수동으로 적용한다. 조건은 둘이다.

- 새 잡 5종이 전환 뒤 1주 동안 실패 없이 돈다.
- 화면 숫자에 이상이 없다.

삭제 SQL 파일은 전환 릴리스에 넣되, 파일 머리와 배포 절차에 "전환 1주 뒤 적용"이라고 적는다. 다른 마이그레이션과 함께 적용되면 유예가 사라진다.

### 되돌리기

- **1단계**: 배포 설정에서 새 CronJob 을 뺀다. `_new` 테이블은 읽는 곳이 없다.
- **2단계 뒤, `_backup` 테이블이 있는 동안**: 통계 CronJob 을 빼고, 이름을 거꾸로 바꾸고(새 테이블에 `_new` 를 붙이고 `_backup` 을 뗀다), 세 앱을 이전 버전으로 다시 올린다. 그 뒤 비는 날짜마다 옛 잡 5종을 날짜를 주어 손으로 돌린다. 원본이 남아 있어 가능하지만 이 비용이 든다.
- **3단계 뒤**: 되돌리지 않는다.

### 옛 통계를 따로 덤프하지 않는 이유

`_backup` 테이블로 1주 남기는 것으로 충분하다고 본다.

- 전환 뒤에는 옛 통계를 읽는 화면이 없다.
- 원본으로 다시 만들 수 없는 것은 원본 보관 기간보다 오래된 구간뿐이고, 그 구간은 1인 통계에만 있다(2026-11-13 운영 기준 1인 승률 343MB, 1인 순위 27MB, 약 98일치로 추정).
- 최근 통계가 더 쓸모 있어, 오래된 구간을 잃는 것은 감수한다.

## 11. 알려진 한계

- **10분보다 오래 걸린 저장**: 원본을 저장하는 트랜잭션이 10분 넘게 열려 있으면 그 전투가 상한 id 아래로 뒤늦게 들어와 집계에서 빠진다. 여유가 충분한지는 재지 않았다.
- **패치 등록마다 하루치 빼기**: 평소 경로다(5.8). 3인 조합은 한 트랜잭션에 수십만 줄을 고칠 것으로 추정하고, 재지 않았다.
- **패치를 고친 뒤의 숫자**: 등록·수정·삭제한 뒤 다음 실행까지 최대 3시간은 옛 범위의 숫자가 보인다.
- **한 유형이 멈추면**: 새 패치가 모든 화면에서 보이지 않고 최근 업데이트도 멈춘다. 문제가 화면에 드러나는 대신 다섯 유형이 서로 묶인다.
- **최근 업데이트의 표시**: 평소 약 50분 전에서 3시간 10분 전 사이를 오간다. 10분 여유, 유형 간 엇갈림 40분, 3시간 주기가 더해진 값이다. 캐시 때문에 숫자와 최대 30분 어긋날 수 있다.
- **범위가 끝난 패치의 최근 업데이트**: 범위 마지막 날의 끝 시각으로 내려 적은 값이라, 실제 마지막 전투보다 조금 늦게 보일 수 있다.
- **새 패치의 첫 몇 시간**: 기본이 가장 최근 패치라, 표본이 몇 시간치일 때 상위 티어와 조합 순위가 거의 비어 보인다.
- **원본 보관 밖의 패치**: 범위의 첫 날이 원본에서 지워진 패치는 통계를 만들지 않고, 지운 통계를 다시 만들 수도 없다.
- **운영에서의 정확성**: 운영 데이터로 "정확히 같다"를 늘 확인할 수단은 없다. 정확성은 테스트가 맡고, 운영에서는 전환 전의 시험 패치로 한 번 확인한다.
- **전환 순간**: 프론트 배포에서 core-api 배포가 끝날 때까지 통계 영역이 준비 중으로 보인다.

## 12. 구현 전에 확인할 것

- 프로젝트가 쓰는 H2 버전에서 두 단계 쓰기가 도는지. 조사에 쓴 것은 2.4.240 이다.
- CronJob 의 시간 제한과 재시도 기본값. 차트 본체가 이 저장소에 없다.
- 상대·2인 조합·3인 조합의 처리 속도와 첫 실행의 DB 부하
- 원본 보관이 45일로 늘어 파티션이 많아졌을 때의 읽기 쿼리 계획 시간. 지금 파티션 10개에서는 계획이 실행보다 오래 걸린다(25.5ms 대 6.1ms).
- 원본 저장 트랜잭션의 길이. 10분 여유의 근거가 된다.
