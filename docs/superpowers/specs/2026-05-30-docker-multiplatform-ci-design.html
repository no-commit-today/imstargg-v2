백엔드 도커 이미지 멀티플랫폼 CI 개선 설계

작성일: 2026-05-30 · 대상: imstargg-backend (core-api / core-worker / core-batch) · 브랜치: dev

1. 배경 & 목표

현재 .github/workflows/deploy.yaml는 (1) build-jar 잡에서 Gradle 로 JAR 을 빌드해 GitHub Actions artifact 로 업로드하고, (2) build-and-push 잡에서 그 JAR 을 내려받아 단순 Dockerfile(COPY app.jar)로 이미지를 만들어 linux/arm64 단일 플랫폼으로 ECR 에 푸시한다. 각 앱마다 거의 동일한 Dockerfile 이 4개(core-api/worker/batch/admin) 존재한다.

목표

  • Java 빌드를 이미지 빌드 시점(멀티스테이지)으로 이동 — 별도 build-jar 잡 + artifact 전달 제거.
  • 레이어드 JAR(Spring Boot 4 jarmode=tools)로 런타임 레이어 캐싱 개선.
  • linux/arm64 빌드. amd64 는 추후 추가되며, 추가 비용이 거의 없도록 설계.
  • 4개 Dockerfile → 단일 파라미터화 Dockerfile 1개로 통합.

비목표 (Out of Scope)

  • amd64 실제 활성화 — 설계상 한 줄 추가로 가능하나 이번 작업에선 arm64 만.
  • CDS / AOT 캐시를 이용한 기동 속도 최적화 (레이아웃은 이미 CDS-friendly, 후속 과제).
  • 런타임 베이스 이미지 슬리밍(distroless/ubi-minimal/alpine).
  • core-admin 배포 파이프라인 구성 (deploy.yaml 대상 외).

3. 설계 결정 & 근거

3.1 bootBuildImage vs Dockerfile → Dockerfile + buildx

항목bootBuildImage (Paketo)Dockerfile + buildx
arm64 / 멀티아치 CI로컬 데몬 아키텍처로만 빌드. 크로스빌드는 QEMU 데몬 빌드라 buildpack 라이프사이클이 매우 느림. manifest list 단일 명령 생성 불가platforms 로 네이티브 지원, manifest list 자동
GHA 빌드 캐시자체 캐싱 모델, type=gha 레이어 캐시와 불일치cache-to/from: type=gha 표준
베이스/레이어 제어제한적완전 제어

결론: 멀티아치 CI 제어가 목표이므로 Dockerfile + buildx.

3.2 단일 vs 개별 Dockerfile → 단일 파라미터화

3개 앱(+admin)은 패키징이 동일하고 차이는 빌드 대상 Gradle 모듈뿐. ARG GRADLE_MODULE 하나로 처리. EXPOSE는 K8s 에서 무시되는 정보성 지시어라 차이 무의미. 기존 4개 Dockerfile 은 모두 삭제하고 imstargg-backend/Dockerfile 1개로 통합. admin 은 필요 시 동일 Dockerfile 에 인자만 바꿔 빌드 가능.

3.3 멀티아치를 싸게 만드는 핵심: --platform=$BUILDPLATFORM 빌더

JAR·추출 레이어는 플랫폼 독립적인 JVM 바이트코드다. 따라서 빌더 스테이지를 빌드 호스트의 네이티브 아키텍처($BUILDPLATFORM=amd64 러너)에 고정한다.

  • 무거운 Gradle/Kotlin 컴파일은 네이티브로 1회만 실행 → arm64 QEMU 에뮬레이션 회피(에뮬레이션 시 컴파일 수 배 지연).
  • 런타임 스테이지는 COPY 만 수행(RUN 없음) → 외래 아키텍처 이미지를 만들어도 실행 단계가 없어 QEMU 자체가 불필요. setup-qemu-action 추가 안 함.
  • 비루트 사용자는 RUN adduser 대신 numeric USER 1000:1000 로 처리해 런타임 스테이지를 RUN-free 로 유지(K8s runAsNonRoot 호환, Spring Boot 동작 무관).
  • amd64 추가 시: 빌더는 여전히 1회 공유 실행, 런타임만 아치별 COPY → 비용 거의 그대로.

3.4 레이어드 JAR — Spring Boot 4 jarmode=tools

참고 Dockerfile 의 java -Djarmode=layertools ... extract는 deprecated. Spring Boot 4.0.3 공식 문서 기준 올바른 방식:

java -Djarmode=tools -jar application.jar extract --layers --destination extracted
# 런타임 ENTRYPOINT 는 추출된 thin jar 를 실행
ENTRYPOINT ["java", "-jar", "application.jar"]

표준 4개 레이어(dependencies, spring-boot-loader, snapshot-dependencies, application)로 분리되어 이미지 pull/rebuild 캐싱이 개선되고, 이 레이아웃은 CDS/AOT-friendly 라 후속 기동 최적화에도 그대로 활용 가능.

3.5 빌드 시점 의존성 캐싱 → prefetch 레이어

GitHub 호스티드 러너는 매 실행 새 VM 이라 캐시 지속이 관건이다. BuildKit --mount=type=cache(캐시 마운트)는 type=gha로 영속화되지 않으므로, 소스가 바뀌는 모든 CI 빌드에서 의존성이 매번 재다운로드된다. 따라서:

  • GRADLE_USER_HOME=/workspace/.gradle 를 캐시 마운트가 아닌 실제 디렉터리로 둔다 → 다운로드된 의존성이 이미지 레이어에 포함되어 type=gha 로 영속 캐싱된다.
  • 빌드 스크립트(build.gradle.kts 12개 + settings/properties/wrapper)만 먼저 COPY → :module:dependencies 로 워밍 → 이 레이어는 빌드 스크립트 해시 기준으로 캐시. 소스만 바뀌면 의존성 재다운로드 없음.
  • 트레이드오프: 모듈 추가 시 Dockerfile 의 COPY 목록을 갱신해야 함(주석으로 명시). gradle.properties(버전) 변경 시 deps 레이어 무효화는 정상(빈도 낮음).

3.6 .dockerignore 필수

COPY . . 가 호스트의 기존 산출물을 끌고 들어오면 (1) find 가 stale jar 를 잡거나 (2) 워밍한 /workspace/.gradle 를 덮어쓴다. imstargg-backend/.dockerignore 로 빌드 산출물·IDE·VCS 를 제외한다. 부수 효과로 빌드 컨텍스트 업로드도 가벼워진다.

4. 산출물

4.1 imstargg-backend/Dockerfile (신규, 단일)

# syntax=docker/dockerfile:1

# ── Builder: 네이티브 플랫폼에서 실행 (Kotlin 컴파일 에뮬레이션 회피) ──
FROM --platform=$BUILDPLATFORM eclipse-temurin:21-jdk-jammy AS builder
ENV GRADLE_USER_HOME=/workspace/.gradle
WORKDIR /workspace
ARG GRADLE_MODULE                       # 예: :core:core-api

# 1) 빌드 스크립트만 먼저 복사 → 의존성 해석 레이어 캐싱
#    (모듈 추가 시 아래 목록 갱신 필요)
COPY gradlew settings.gradle.kts gradle.properties build.gradle.kts ./
COPY gradle ./gradle
COPY core/core-enum/build.gradle.kts            ./core/core-enum/
COPY core/core-api/build.gradle.kts             ./core/core-api/
COPY core/core-admin/build.gradle.kts           ./core/core-admin/
COPY core/core-batch/build.gradle.kts           ./core/core-batch/
COPY core/core-worker/build.gradle.kts          ./core/core-worker/
COPY infrastructure/db-core/build.gradle.kts    ./infrastructure/db-core/
COPY infrastructure/redis-core/build.gradle.kts ./infrastructure/redis-core/
COPY infrastructure/aws-sqs/build.gradle.kts    ./infrastructure/aws-sqs/
COPY infrastructure/aws-s3/build.gradle.kts     ./infrastructure/aws-s3/
COPY client/brawlstars-client/build.gradle.kts  ./client/brawlstars-client/
COPY support/logging/build.gradle.kts           ./support/logging/
COPY support/monitoring/build.gradle.kts        ./support/monitoring/
RUN chmod +x gradlew && ./gradlew ${GRADLE_MODULE}:dependencies --no-daemon

# 2) 소스 복사 후 bootJar + 레이어 추출 (jarmode=tools, Spring Boot 4)
#    GRADLE_MODULE(:core:core-api) → 파일경로(core/core-api)로 변환해 해당 모듈 build/libs 만 탐색
#    (트리 전체를 뒤지면 의존 라이브러리 모듈의 jar 를 잘못 집을 수 있음)
COPY . .
RUN ./gradlew ${GRADLE_MODULE}:bootJar -x test --no-daemon --build-cache --parallel \
 && MODULE_PATH="$(echo "${GRADLE_MODULE#:}" | tr ':' '/')" \
 && cp "$(find ${MODULE_PATH}/build/libs -name '*.jar' -not -name '*-plain.jar' | head -n1)" application.jar \
 && java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# ── Runtime: 타깃 플랫폼(arm64). COPY 만 → QEMU 불필요 ──
FROM eclipse-temurin:21-jre-jammy
WORKDIR /app
COPY --from=builder --chown=1000:1000 /workspace/extracted/dependencies/ ./
COPY --from=builder --chown=1000:1000 /workspace/extracted/spring-boot-loader/ ./
COPY --from=builder --chown=1000:1000 /workspace/extracted/snapshot-dependencies/ ./
COPY --from=builder --chown=1000:1000 /workspace/extracted/application/ ./
USER 1000:1000
ENTRYPOINT ["java", "-jar", "application.jar"]

6. 검증 계획

  • 로컬(Apple Silicon = arm64 네이티브): docker buildx build --platform linux/arm64 --build-arg GRADLE_MODULE=:core:core-api -f imstargg-backend/Dockerfile imstargg-backend --load 로 빌드 성공 확인.
  • 기동: docker run 으로 이미지가 부팅 단계까지 진입하는지 확인(외부 의존성 전까지).
  • 캐싱: 소스만 살짝 바꿔 2회차 빌드 시 의존성 재다운로드가 없고 deps 레이어가 캐시 히트하는지 로그로 확인.
  • CI: workflow_dispatch 로 한 앱(core-api) 배포 → ECR manifest 가 linux/arm64 단일인지, K8s 가 정상 pull 하는지 확인.
  • core-worker / core-batch 도 동일 인자만 바꿔 빌드 성공 확인.

7. amd64 추가 시 (후속)

platforms: linux/arm64 → linux/amd64,linux/arm64 한 줄. 빌더는 $BUILDPLATFORM 고정이라 여전히 1회만 실행되고, 런타임 스테이지는 RUN-free 라 QEMU 없이 아치별 COPY 로 manifest list 가 생성된다.
