## 1. 배경

지금 산식은 `점수 = 50 + 200 × (수축 승률 − 맥락 평균 승률) × 가중` 이다. 가중은 픽률로 정하고 0.1 ~ 1.0 이다. 등급은 S ≥ 55, A ≥ 52, B ≥ 48, C ≥ 45 다.

- **픽률을 곱하는 방식이 뜻과 맞지 않는다.** 가중은 평균과의 차이를 줄이기만 한다. 덜 쓰이는 브롤러는 승률이 높아도 낮아도 50 근처로 눌린다. 승률이 평균보다 낮은 브롤러는 인기가 높을수록 점수가 더 깎인다. 스펙 A 부록 A.5 가 이것을 "신뢰도 보정이 아니라 인기 감점" 이라고 적었다. 신뢰도는 수축이 이미 맡는다.
- **표본이 적어도 등급이 붙는다.** 전투가 몇 판뿐인 브롤러도 S ~ D 중 하나를 받는다. 전투가 0판인 브롤러는 프론트가 D 로 그린다.
- **다른 사이트는 픽률을 더한다.** lol.ps 와 op.gg 의 점수를 역산하니 둘 다 `ln(픽률)` 을 승률에 더하는 모양이었다. op.gg 에서 픽률 e배는 승률 1.9%p 에 해당한다([부록 C2.2](#c22-외부-사이트)). 관측 범위에서 포화는 보이지 않았다.
- **봇을 뺀 데이터로 다시 쟀다.** 운영 원본 10일치(2026-10-30 ~ 11-08)에서 스펙 C1 규칙으로 봇 전투를 빼고 후보 산식과 등급 규칙을 비교했다([부록 C2](#부록-c2-분석-근거-2026-11-09--10)).

## 3. 설계

### 3.1 산식

입력은 한 맥락에서 브롤러마다 합친 승·패·무다. 조회 결과에 행이 있는 브롤러만 입력이다.

| 기호 | 정의 |
|---|---|
| n | 브롤러의 전투 수 = 승 + 패 + 무. 응답의 `battleCount` 와 같은 수다 |
| wr | 브롤러의 승률 = 승 ÷ (승 + 패). 승 + 패가 0 이면 0 |
| μ | 맥락 평균 승률 = Σ승 ÷ Σ(승 + 패). 입력 전체의 합이다. 분모가 0 이면 0 |
| adj | 수축 승률 = (n × wr + 300 × μ) ÷ (n + 300) |
| m | 등급을 받는 브롤러(n 이 300 이상, §3.2)들의 n 의 중앙값. 그 수가 짝수면 가운데 두 값의 평균 |
| 가산 | 4 × tanh( ln(n ÷ m) ÷ ln 3 ) |

```
점수 = 반올림( max(0, 50 + 200 × (adj − μ) + 가산) )
```

- **n ÷ m 은 픽률 ÷ 픽률 중앙값과 같다.** 픽률의 분모(맥락의 게임 수)가 같아 약분된다.
- **중앙값은 등급을 받는 브롤러만으로 낸다.** 표본이 적은 브롤러까지 넣으면, 그들이 과반인 맥락(맵 하나, 상위 티어 구간)에서 m 이 300 아래로 내려간다. 그러면 등급을 받는 브롤러가 모두 +3 ~ +4점을 받는다. 가산이 브롤러를 가르지 못하고 그 맥락의 등급만 위로 민다([부록 C2.12](#c212-중앙값을-내는-대상-2026-11-10-개정)).
  - 표본이 적은 브롤러의 가산도 같은 m 으로 낸다.
  - μ 는 입력 전체로 낸다. 바뀌지 않는다.
- **경계 처리**
  - 입력이 비면 결과도 빈다.
  - 등급을 받는 브롤러가 없으면 모든 브롤러의 가산은 0 이다. n 이 0 인 브롤러도 0 이다.
  - 등급을 받는 브롤러가 있고 n 이 0 이면 가산은 −4 다(식의 극한값).
- **계산 순서**: 0 아래를 0 으로 올린 뒤 정수로 반올림하고(지금과 같은 `roundToInt`), 등급은 그 정수로 정한다.
- **조회 맥락마다 달라진다.** μ 와 m 이 맥락에서 나오므로 같은 브롤러도 기간·티어·맵이 바뀌면 점수가 달라진다. 지금 산식도 같다. 기간을 넓혀 등급을 받는 브롤러가 늘면 m 이 내려가 가산이 조금 오른다(§7).

상수는 다섯 개다.

| 상수 | 값 | 뜻 |
|---|---|---|
| 수축 강도 | 300 | 평균 쪽으로 당기는 판수. 지금 값(`BAYESIAN_C`) 그대로 |
| 배율 | 200 | 승률 1%p 가 2점. 지금 값(`SCALING_K`) 그대로 |
| 가산 상한 | 4 | 인기 가산의 최대 크기(점). 승률 2%p 에 해당한다 |
| 포화 배수 | 3 | 픽률이 중앙값의 3배일 때 가산이 상한의 76%(tanh 1)다. 식에는 ln 3 으로 들어간다 |
| 표본 하한 | 300 | 등급을 매기는 최소 전투 수(§3.2) |

가산의 크기는 아래와 같다.

| 픽률 ÷ 중앙값 | 0.1 | 1/3 | 0.5 | 1 | 2 | 3 | 10 | 100 |
|---|---|---|---|---|---|---|---|---|
| 가산(점) | −3.88 | −3.05 | −2.23 | 0 | +2.23 | +3.05 | +3.88 | +4.00 |

- 중앙값 근처의 기울기는 4 ÷ ln 3 = 3.64점(승률 1.82%p)이다. op.gg 의 1.9%p 와 같은 수준이다.
- **인기만으로는 등급이 바뀌지 않는다.** 수축 승률이 평균과 같으면 점수는 46 ~ 54 이고 등급은 B 다. A 는 55 이상, C 는 44 이하다.

### 3.2 등급과 표본 부족

| 조건 | 등급 |
|---|---|
| n < 300 | 없음(표본 부족) |
| 점수 ≥ 60 | S |
| 점수 ≥ 55 | A |
| 점수 ≥ 45 | B |
| 점수 ≥ 40 | C |
| 그 밖 | D |

- 표본 부족은 등급 값이 아니다. 등급이 없는 상태다. `TierGrade` 에 값을 더하지 않는다.
- 표본 하한은 수축 강도와 같은 300 이다. n 이 300 이면 수축 승률이 자기 승률과 평균의 정확히 중간이다. 그보다 적으면 점수의 절반 이상이 평균값이다.
- 등급이 없어도 점수는 계산해 응답에 싣는다. 화면은 등급 없는 브롤러의 점수를 순서를 정하는 데만 쓴다(§3.5).
- 화면의 전투수 열이 300 미만이면 표본 부족이다. 사용자가 표에서 바로 확인할 수 있다.

### 3.3 응답 (core-api)

1인 통계 응답(`BrawlerResultStatisticsItemResponse`)만 바뀐다.

| 필드 | 지금 | 바뀐 뒤 |
|---|---|---|
| `tierScore` | 정수 | 정수(그대로). 등급이 없어도 값이 있다 |
| `tier` | `"S"` ~ `"D"` | `"S"` ~ `"D"` 또는 `null`(표본 부족) |

- 항목 순서: 등급 있는 항목이 먼저다. 그 안에서 점수 내림차순, 점수가 같으면 전투 수 내림차순이다. 등급 없는 항목도 같은 기준으로 뒤에 놓는다.
- 전투가 0판인 브롤러는 지금처럼 항목 자체가 없다.
- 구버전 프론트는 `null` 을 D 로 그린다(`parseTier` 의 기본값). 백엔드를 먼저 배포해도 화면이 깨지지 않는다. 같은 릴리즈에서 프론트를 이어 배포한다.

### 3.4 코드 구조 (core-api)

- **1인 전용 타입 `BrawlerTierScore`** 를 `domain/statistics` 에 새로 둔다. 점수(`value: Int`)와 등급(`grade: TierGrade?`)을 함께 갖는다. 산식, 상수, 등급 판정이 이 타입에 모인다. 근거와 결정 이력은 `ComboStatsPolicy` 처럼 KDoc 에 적는다.
- `BrawlerResultStatisticsItem.tierScore` 의 타입을 `BrawlerTierScore` 로 바꾼다. `BrawlerResultStatistics.create` 가 새 타입으로 점수를 내고 §3.3 의 순서로 정렬한다.
- **기존 `TierScore` 와의 관계.** 조합 네 곳(`BrawlerPairResultStatistics`, `BrawlerTrioResultStatistics`, `PairResultRanking`, `TrioResultRanking`)이 `TierScore` 를 쓴다. 조합 등급은 "조합 통계 배포 전 정정" 스펙이 지운다. 두 스펙의 구현 순서는 정하지 않았으므로 구현 시점의 상태에 따라 아래처럼 한다.
  - 조합 호출부가 남아 있으면: `TierScore` 의 산식과 등급 경계는 그대로 둔다. 1인만 쓰던 `pickRateWeight = true` 분기와 그 상수(`LOG_ALPHA`, `MIN_WEIGHT_BETA`), 그 테스트를 지우고 조합 호출부 네 곳은 인자만 뺀다. KDoc 의 1인 설명을 고친다.
  - 조합 호출부가 이미 없으면: `TierScore` 와 `TierScoreTest` 를 지운다.
- **캐시 키**: `BattleResultStatisticsRepositoryWithCache.findBrawlerResultStatistics` 의 키를 `v3:brawlerResultStats:` 에서 `v4:brawlerResultStats:` 로 올린다. 다른 키는 그대로다.
- **이름**: 새 상수 이름은 구현 계획에서 용어 사전(`docs/superglossary/glossary.md`)에 맞춰 정한다. 사전에 없는 단어(중앙값, 가산, 상한, 포화)는 `/superglossary:glossary` 로 먼저 등록한다.
- core-batch, core-worker, DB 스키마는 바꾸지 않는다.

### 3.5 화면 (imstargg-frontend)

**타입과 매퍼**

- 응답 타입의 `tier` 는 `string | null`, 도메인 타입 `BrawlerResultStat.tier` 는 `StatTier | null` 이다.
- 1인 매퍼는 값이 `"S"` ~ `"D"` 이면 그 등급, 아니면(`null`, 누락, 모르는 문자열) `null` 로 바꾼다. 조합 매퍼가 쓰는 `parseTier`(기본값 D)는 그대로 둔다.

**등급 표시** (`TierBadge`)

- `tier` 가 `null` 이면 "–" 를 그린다. `aria-label` 과 `title` 은 "표본 부족" 이다.
- D 배지(회색으로 채운 원)와 구분되게 채우지 않은 테두리 원으로 그린다. 색은 표의 보조 글자색(`#5C6271`)을 쓴다.
- 티어 열은 모바일에서 36px 이라 "표본 부족" 글자를 넣을 수 없다. 그래서 기호와 범례로 알린다.
- 통계가 없는 브롤러(`stat` 이 `null`)도 같은 배지를 쓴다. 지금은 D 배지다(`BrawlerStatRow`).

**범례**

- `/brawlers` 브롤러 탭의 표(`BrawlerStatTable`)와 이벤트 상세의 결과형 표(`EventResultStatsTable`) 아래에 한 줄을 둔다. 지금 보이는 행 중 등급 없는 행이 있을 때만 그린다.

  > – 표본 부족: 전투 수가 적어 티어를 매기지 않습니다.

- 문구에 판수(300)를 적지 않는다. 기준이 바뀌어도 화면 문구를 고치지 않게 한다.

**정렬**

- 티어 열로 정렬할 때 등급 없는 행은 오름차순·내림차순과 관계없이 아래에 놓는다. 등급 있는 행끼리, 등급 없는 행끼리는 `tierScore` 로 정렬한다. `stat` 이 없는 행의 점수는 0 으로 본다.
- 이 비교 규칙은 두 표가 같아야 하므로 `src/domain/statistics/sort.ts` 에 함수 하나로 두고 두 표가 함께 쓴다.
- 다른 열(승률, 픽률, 스타플레이어 비율, 전투수, 이름)의 정렬은 바꾸지 않는다.

**행 강조(레일)**

- 등급 없는 행은 순위와 관계없이 `neutral` 레일이다. 1 ~ 3위의 금·은·동 레일도 받지 않는다. 표본이 적은 행이 승률 정렬에서 금색으로 강조되지 않게 한다.
- 등급 있는 행은 지금과 같다(1 ~ 3위 금·은·동, 그 밖은 S `win`, A·B `neutral`, C·D `loss`).
- 순위 숫자 열은 지금처럼 정렬된 순서의 번호다.

**통계가 0건인 기간**

- `/brawlers` 브롤러 탭은 전 브롤러를 "–" 배지, `neutral` 레일로 그리고 범례를 보인다. 스펙 C1 이 그대로 두기로 한 "전 브롤러 티어 D, 1 ~ 3위 금·은·동" 표시가 이렇게 바뀐다. 승률 0.0%, 전투수 0 표시와 머리말은 그대로다.

**소개 페이지** (`app/about/page.tsx`)

- "데이터 출처와 갱신" 앞에 "티어 산정 방식" 문단을 더한다.

  > 브롤러 티어(S~D)는 승률과 픽률을 함께 반영한 점수로 매깁니다. 승률은 선택한 조건(티어 구간·기간·맵)의 평균과 비교하며, 전투 수가 적은 브롤러의 승률은 평균 쪽으로 보정합니다. 픽률이 높으면 점수를 조금 더하고 낮으면 조금 빼지만, 그 폭에는 상한이 있어 승률이 평균 수준인 브롤러가 픽률만으로 높은 티어를 받지는 않습니다. 전투 수가 기준보다 적은 브롤러는 티어를 매기지 않고 "–"(표본 부족)로 표시합니다. 브롤러 메타 페이지의 통계는 젬 그랩·브롤 볼 같은 3대3 모드의 전투를 합친 값이며, 쇼다운은 포함하지 않습니다.

**바꾸지 않는 화면**: 조합 표 세 개(`PairStatsTable`, `TrioStatsTable`, `ComboRankingTable`)와 카운터 표. `TierBadge` 에 지금처럼 등급 값을 넘긴다. 1인 통계 응답을 쓰는 화면은 위의 두 표뿐이다.

**통계·응답 테스트**

- `BrawlerResultStatisticsTest`: 항목 순서(등급 있는 항목 먼저, 점수, 전투 수), 표본이 적은 항목의 등급 없음.
- `BrawlerResultStatisticsResponseTest`: 등급이 없으면 `tier` 가 `null` 이고 `tierScore` 는 값이 있다.
- `StatisticsCacheKeyTest`: 1인 통계 키가 `v4:` 로 시작한다.
- `CacheConfigSerializerTest`: 등급이 있는 항목과 없는 항목이 직렬화 왕복에서 그대로다.
- `TierScoreTest` 와 조합 테스트는 §3.4 의 두 경우에 맞춰 고치거나 지운다.

**프론트 테스트**

- 1인 매퍼: `"S"` 는 S, `null`·누락·모르는 문자열은 `null`.
- `TierBadge`: `null` 이면 "–" 와 `aria-label` "표본 부족".
- 정렬 함수: 내림차순과 오름차순 모두 등급 없는 행이 아래. 등급 없는 행끼리는 점수순.
- 두 표: 등급 없는 1위 행이 `neutral` 레일이다. 등급 없는 행이 있으면 범례가 보이고 없으면 보이지 않는다. 통계가 없는 브롤러 행이 "–" 배지다.
- 기존 테스트 중 D 배지나 금·은·동 레일을 기대하는 것은 새 규칙에 맞춘다.
- e2e(`tests/e2e/statistics.spec.ts`)는 등급 배지나 레일을 단언하지 않아 고치지 않는다.

**실행**: `imstargg-backend` 에서 `./gradlew test`(컨텍스트 테스트 포함)와 `./gradlew ktlintCheck`. `imstargg-frontend` 에서 `pnpm typecheck`, `pnpm lint`, `pnpm test:run`.

**배포 후 검증**: 운영 API 의 기본 조건(전체 이벤트, 최근 기간)에서 티어 구간별 등급 수를 [부록 C2.9](#c29-이-설계로-나오는-등급) 의 표와 견준다. 스펙 C1 재집계와 스펙 D 가 적용되기 전이면 표본 부족이 표보다 많다(§7).

## 6. 문서·버전

- 문서는 §3.6 대로 고친다.
- 버전: core-api 와 frontend 가 바뀐다. PR 단계에서 `/release` 로 확인한다. core-batch 와 core-worker 는 바뀌지 않는다.
- 릴리즈 노트에 적을 것
  - 브롤러 티어의 산정 방식이 바뀌어 등급이 넓게 바뀐다. 트로피 티어는 S·A 가 많고 D 가 드물다([부록 C2.9](#c29-이-설계로-나오는-등급)).
  - 전투 수가 적은 브롤러는 등급 대신 "–"(표본 부족)로 보인다. 맵 페이지와 상위 티어 구간에서 많다.
  - 1인 통계 응답의 `tier` 가 `null` 일 수 있다.
  - 스펙 C1 의 릴리즈 노트 항목 중 "0건인 기간에 전 브롤러를 티어 D 로 그린다" 는 "표본 부족으로 그린다" 로 바꿔 적는다.
  - 마이그레이션 필요 사항: 없다. 배포 순서는 백엔드, 프론트 순이다.
  - 롤백 시 주의 사항: 이미지 태그를 되돌리면 된다. 캐시 키가 `v3:` 로 돌아가고 `v4:` 항목은 30분 뒤 사라진다.

- 두 사이트 모두 `ln(픽률)` 을 승률에 더하는 모양이 가장 잘 맞았다. 승률과 픽률을 곱하는 항은 1차 근사에서 필요하지 않았다.
- 픽률 e배에 해당하는 승률: op.gg 1.91%p, 1.93%p. lol.ps 1.68%p, 2.56%p.
- 라인 중앙값의 0.2배 ~ 10배 범위에서 포화는 관측되지 않았다. 수축도 감지되지 않았다. 밴률의 몫은 작다(밴률 10%p 가 승률 0.2 ~ 0.7%p).
- op.gg 도움말은 티어를 비공개 알고리즘으로 계산하고 승률·픽률·밴률 말고도 입력이 있다고 적는다. 위 값은 역산한 근사다.
- 그래서 "픽률이 높다고 계속 오르면 안 된다" 는 상한은 사이트에서 온 것이 아니라 우리 설계 조건이다(결정 2).

### C2.3 인기 가산의 계수와 상한

- 기울기는 사이트 등가(1.7 ~ 2.6%p)의 가운데인 op.gg 값 근처로 잡았다. 4 ÷ ln 3 = 3.64점 = 1.82%p.
- 상한 4점은 A 경계까지의 거리(반올림을 넣어 4.5점)보다 작게 잡았다. 인기만으로 등급이 오르지 않는다.
- 포화 배수 3 은 픽률이 중앙값의 3배면 상한의 76%, 10배면 97% 에 닿게 한다.
- 트로피 티어는 봇을 뺀 뒤에도 픽률이 높은 브롤러의 승률이 낮다(T1000+ 의 픽률·승률 상관 −0.35, 판수 가중 기울기는 ln 픽률 1 단위당 −1.88%p). 경쟁전 티어의 상관은 0 ~ +0.1 이다. 트로피전에서 가산은 주로 이 차이를 메우는 쪽으로 움직인다.
- 상한 없는 로그 가산(사이트 방식)은 결정 2 에 어긋나 택하지 않았다. 곱 가중(지금 방식)은 승률이 평균보다 낮을 때 인기가 감점을 키운다.
- 낮은 픽률의 감점만 줄이는 비대칭 안은 택하지 않았다. 위아래가 같은 모양이다(결정 3).

| 비율 10/20/40/20/10% | 0.60 ~ 0.72 | 0.49 ~ 0.52 | 0.87 ~ 0.90 | 0.72 ~ 0.77 | 0.32 ~ 0.33 | 0.13 ~ 0.20 |

- 경계 후보 58/54/46/42 와 57/53/47/43 은 S 가 더 많다(T1000+ 21 ~ 30%).
- T3000+ 와 MASTER+ 는 어느 규칙으로도 일치도가 낮다. 이 맥락의 브롤러는 대부분 표본 부족이 된다([C2.5](#c25-표본-기준)).

### C2.6 수축 강도

- 전체 이벤트 맥락은 수축 강도에 무관하다(예측 오차 차이 0.001%p 이하). 브롤러당 판수가 수천 이상이기 때문이다.
- 맵 페이지에서는 50 ~ 100 이 승률 예측에 가장 맞다. T1000+ 맵 페이지의 예측 오차가 300 일 때 2.264%p, 최적값에서 2.159%p 다(약 5%). MASTER+ 는 300 이 최적이다.

### C2.7 기준 평균

- μ 는 슬롯 가중 평균이다. 트로피 티어는 픽률이 아주 높은 브롤러의 승률이 낮아(MORTIS 픽률 33%, 승률 42.4%) 보통 브롤러의 승률이 μ 보다 높다. T1000+ 의 브롤러 수축 승률 중앙값이 51.2 ~ 51.5%, T2000+ 는 μ 47.33% 에 중앙값 49.08% 다.

- 전부로 내면 표본이 적은 브롤러가 과반인 맵에서 중앙값이 300판 아래다. 등급을 받는 브롤러는 모두 그 위라서 가산이 상한 근처에 몰린다. 가산이 브롤러를 가르지 못하고, C·D 가 거의 나오지 않는다.
- 등급 받는 브롤러만으로 내면 가산 평균이 어느 맥락에서나 0 근처다.

**전체 이벤트 화면(최근 7일)의 변화.**

- T1000+, T2000+, MYTHIC+, LEGEND+ 는 300판 미만인 브롤러가 없어 점수와 등급이 모두 같다.

- T3000+ 는 중앙값이 33판에서 506판이 된다. 등급을 받는 6명 중 4명의 등급이 한 칸 내려간다(MORTIS 55 A → 52 B, NORI 55 A → 51 B, MELODIE 56 A → 50 B, EDGAR 48 B → 43 C).

**치르는 값.** 맵 페이지에서 두 조건 모두 등급을 받는 브롤러를 견줬다.

| 견준 것 | 값 | T1000+ | T2000+ | MYTHIC+ | LEGEND+ | MASTER+ |
|---|---|---|---|---|---|---|
| 3일 → 10일 | 등급이 같은 비율: 전부 → 등급 받는 브롤러 | 91% → 91% | 92% → 90% | 82% → 83% | 78% → 77% | 76% → 73% |
| 3일 → 10일 | 점수 차 평균(넓힌 쪽 − 좁은 쪽) | −0.00 → +0.32 | +0.09 → +0.38 | −0.19 → +0.04 | −0.09 → +0.62 | +0.16 → +1.27 |
| 7일 → 10일 | 등급이 같은 비율 | 96% → 96% | 97% → 95% | 92% → 93% | 90% → 89% | 90% → 90% |

- 등급이 같은 비율은 MYTHIC+ 에서 같거나 1%p 오르고, 나머지 구간에서 0 ~ 3%p 낮아진다. 낮아지는 것은 등급을 받는 브롤러의 집합이 바뀌면 중앙값이 따라 움직이기 때문이다.
- 기간을 넓히면 등급을 받는 브롤러가 늘어 중앙값이 내려가고 점수가 조금 오른다. MASTER+ 맵 페이지가 가장 크다(3일 → 10일에 +1.27점).
- MASTER+ 의 κ 가 0.39 에서 0.24 로 내려간다. 등급이 같은 비율은 62% 에서 60% 로 2%p 차이다. κ 는 229행으로 낸 값이다.
- T3000+ 는 맵 페이지에 두 조건 모두 등급을 받는 브롤러가 거의 없어 잴 수 없다.

**택하지 않은 안: 전부로 내는 처음 설계를 그대로 두기.** 가산이 기간과 표본 크기에 따라 움직이지 않고 위 값도 치르지 않는다. 대신 표본이 적은 브롤러가 과반인 맥락에서 가산이 상수(+4 근처)가 되어 등급만 한 칸 올린다. 등급의 뜻이 화면마다 달라진다(MASTER+ 맵 페이지의 S·A 가 46%, 같은 구간 전체 이벤트 화면은 26%).
