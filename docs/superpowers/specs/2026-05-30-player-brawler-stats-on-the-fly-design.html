플레이어 브롤러 통계 — 온더플라이 계산 + Redis 캐시 설계

작성일: 2026-05-30 · 이슈: #38 (플레이어 브롤러 통계 테이블 제거) · 대상: imstargg-backend (core-api · core-worker · redis-core · db-core)

1. 배경 & 목표

현재 플레이어 브롤러 통계는 쓰기 시점 사전집계 방식이다. 플레이어 갱신 시 core-worker 의 PlayerBrawlerStatsAccumulator 가 신규 배틀을 시즌별로 증분 집계하여 player_brawler_stats / player_brawler_stats_item 테이블에 적재하고, core-api 는 이 테이블을 읽기만 한다.

이 사전집계 테이블은 battle 데이터의 파생물일 뿐이다. battle 은 영구 보존(삭제 로직 부재)되므로 통계는 언제든 battle 에서 재계산할 수 있고, 별도 테이블·증분 적재 경로는 중복이다.

목표

  • 읽기 시점 계산: API 호출 시 해당 기간의 battle 을 SQL 집계해 결과 생성.
  • 결과 캐싱: redis-core 에 플레이어별 Redis Hash 로 캐싱.
  • 쓰기 경로 무효화: 플레이어 갱신 시 워커가 해당 플레이어 캐시를 무효화(증분 적재 대신).
  • 테이블·코드 제거: player_brawler_stats(_item) 테이블, PlayerBrawlerStatsAccumulator, 관련 엔티티·JPA 리포지토리 일괄 제거.

비목표 (Out of Scope)

  • 다른 통계(브롤러 전역 통계, stats_* 등) 계산/저장 방식 변경 — 본 작업 무관.
  • 배틀 보존/아카이빙 정책 변경.
  • 프론트엔드 변경 — API 요청/응답 스펙은 동일 유지(내부 구현만 교체)이므로 동기화 불필요.

2. 현재 구조 (코드 확인 결과)

항목확인 내용
읽기 경로PlayerStatisticsQueryComposer → PlayerBrawlerStatsService.get(tag, type, startBattleDate, endBattleDate) → PlayerBrawlerStatsRepository.find() (두 테이블 조회). 시즌 start/end 는 호출부가 BrawlPassSeason/SoloRankSeason 에서 이미 보유

3. 설계 결정 & 근거

3.1 제거 범위 → 한 PR 일괄 제거

battle 영구 보존으로 통계는 항상 재계산 가능 → 테이블 DROP 에 데이터 손실 위험 없음. 계산+캐시 도입 · accumulator/엔티티/리포지토리 제거 · 테이블 DROP 마이그레이션을 한 PR로 진행. (단계적 제거/드롭 보류 대비 코드가 가장 깔끔)

전제: battle 테이블엔 없는데 player_brawler_stats 에만 존재하는 과거 백필 데이터가 없어야 한다. 현재 코드상 모든 통계는 배틀 적재 경로에서만 생성됨 → 위험 없음으로 간주.

3.2 계산 방식 → SQL 집계 (GROUP BY)

항목SQL GROUP BY (채택)앱 측 1000개 배치 집계 (이슈 원안)
반환 데이터브롤러×결과 카운트만 — 최대 (브롤러수×3) 수십 행raw battle 수천 행을 앱으로 적재
I/O · 메모리한 번의 쿼리, 페이지네이션 불필요keyset 반복 조회 + 앱 집계
코드량QueryDSL 쿼리 + 매핑배치 루프 + 집계 로직
적합 조건시즌이 호출부에서 고정 → SQL 로 충분집계 로직이 SQL 로 표현 불가할 때만 이점

결론: 읽기 시점에 시즌 범위가 이미 고정이라 배틀별 시즌 판정이 불필요 → 단일 GROUP BY 로 충분하고 압도적으로 효율적.

3.3 캐시 계층 → redis-core 전용 스토어 + 플레이어별 Hash

항목redis-core 전용 스토어 + Hash (채택)Spring @Cacheable 확장
모듈 간 키 공유키·직렬화 단일 정의, core-api/worker 공통 의존Spring Cache 내부 키 포맷에 worker 수동 삭제가 결합 — 취약
플레이어 단위 무효화DEL 한 번에 전 시즌·타입 제거 (Hash)flat key — 모든 (타입,시즌) 키 열거 또는 SCAN 필요
부분 갱신 동시성시즌별 HSET 은 서로 다른 field → 충돌 없음—
구현 선택: 이 패턴(부분 put + 플레이어 단위 일괄 evict)은 @RedisHash 엔티티보다 StringRedisTemplate 해시 연산(HGET/HSET/EXPIRE/DEL)이 더 적합하다. @RedisHash 는 엔트리마다 독립 키일 때 유리하고, 한 플레이어 해시의 시즌 field 를 부분 갱신하는 모델과 어긋난다.

4. 아키텍처 / 데이터 흐름

5. 컴포넌트 상세

5.A db-core — 집계 쿼리 (QueryDSL)

입력 (playerId, battleTypeCode, startAt, endAt: OffsetDateTime), 출력 (brawlerBrawlStarsId, resultCode, count) 행.

select tp.brawler.brawlStarsId, b.result, count(b)
from   BattleEntity b
join   BattleTeamPlayerEntity tp on tp.battle = b and tp.brawlStarsTag = :playerTag
where  b.player.id = :playerId
  and  b.type      = :battleTypeCode            // "ranked" | "soloRanked"
  and  b.battleAt >= :startAt and b.battleAt < :endAt   // 시즌 정시 경계
  and  b.result is not null
group by tp.brawler.brawlStarsId, b.result
  • 본인 브롤러는 tp.brawlStarsTag = :playerTag 조인으로 자연 격리 → 본인 미참여 배틀 자동 제외, 배틀당 1행이라 중복 카운트 없음.
  • 인덱스 ix_battle__playerid_battleat 로 player+기간 필터, ix_battleteamplayer__battleid 로 조인.

5.B redis-core — PlayerBrawlerStatsCacheStore (신규)

이 모듈의 첫 Kotlin 코드. StringRedisTemplate + Jackson ObjectMapper(Kotlin module) 기반. 값은 primitive DTO 를 JSON 문자열로 직렬화해 hash field 값으로 저장(다형성 타이핑 회피 → 역직렬화 견고).

요소정의
Hash 키playerBrawlerStats:v1:{playerTag} — CLAUDE.md 의 Redis 메서드별 v{N}: 버전 prefix 규약 준수
Field{battleType.name}:{startBattleDate} (예: RANKED:2026-05-01)
값 DTO{ endBattleDate: LocalDate, items: [{ brawlerId: Long, victoryCount, defeatCount, drawCount: Int }] }
findHGET → 역직렬화 (miss/오류 → null)
putHSET + EXPIRE(키 단위 TTL 1h, 튜닝 가능)
evictDEL — 해당 플레이어 전 시즌·타입 일괄 제거

복원력: Redis 장애 시 find→null(=재계산), put/evict→로그 후 무시. 기존 RedisFallbackCacheErrorHandler 철학과 일치. (단, evict 실패 시 다음 TTL 만료까지 stale 가능 — §6 참조)

설정: redis-core 에 전용 RedisTemplate/ObjectMapper 빈 + 캐시 스토어 컴포넌트 제공. core-api/core-worker 가 컴포넌트 스캔으로 주입받도록 구성.

5.C core-api 배선

  • PlayerBrawlerStatsRepository.compute(tag, type, startAt, endAt): 5.A 호출 → resultCode → BattleResult 매핑(미지정/null 무시) → 브롤러별 ResultCount 집계 → 도메인 PlayerBrawlerStats. 플레이어 미존재/배틀 없음 → 빈 items(기존 동작 유지).
  • PlayerBrawlerStatsRepositoryWithCache.find(...): redis-core 스토어로 cache-aside. 기존 *WithCache 패턴의 변형 — 모듈 간 공유 때문에 @Cacheable 대신 명시적 스토어 사용. 그 이유를 KDoc 으로 명시.
  • PlayerBrawlerStatsService.get(...): WithCache 위임. 시그니처 변경 — startBattleDate/endBattleDate: LocalDate → startAt/endAt: OffsetDateTime(시즌 정시 경계). 응답·캐시키용 LocalDate 는 내부에서 .toLocalDate() 유도.
  • PlayerStatisticsQueryComposer: season.startAt.toLocalDate() 전달 → season.startAt(OffsetDateTime) 전달로 변경.

5.D core-worker 무효화

  • core-worker/build.gradle.kts 에 implementation(project(":infrastructure:redis-core")) 추가.
  • PlayerUpdater.update(): playerBrawlerStatsAccumulator.accumulate(...) 제거. newBattles 비어있지 않으면 커밋 후(TransactionSynchronization.afterCommit) cacheStore.evict(playerTag).
  • 커밋 전 DEL 은 동시 읽기가 신규 배틀 미반영 상태로 재적재할 수 있어 afterCommit 으로 순서 보장.
  • updatePlayer()(PlayerRefreshService, 배틀 없음)는 무효화 불필요.

6. 정합성 & 동시성

  • 집계 정합성(시즌 경계): accumulator 는 배틀마다 BrawlPassSeason.of(battleAt) 로 시즌을 판정한다. 따라서 계산 쿼리도 LocalDate 자정이 아니라 시즌 정시 경계(startAt ≤ battleAt < endAt, OffsetDateTime)로 필터해야 결과가 정확히 일치한다. → Service 시그니처를 OffsetDateTime 으로 바꾸는 핵심 이유.
  • SOLO_RANKED 첫 시즌 이전: 호출부가 특정 SoloRankSeason 범위를 넘기므로 accumulator 의 "첫 시즌 이전 배틀 제외"가 범위 필터로 자연 처리된다.
  • SOLO_RANKED 시즌 경계 (의도된 차이, #38): 경계를 반열림 [startAt, endAt) 로 통일한다. RANKED(연속 시즌)는 구 accumulator 와 완전 일치. 그러나 SoloRankSeason 은 endAt 포함 + 시즌 사이 ~24h 공백이 있어, 구 SoloRankSeason.of() 는 그 공백 구간·정확히 endAt 순간의 배틀도 해당 시즌에 귀속시켰다. 반열림 필터는 이 경계 배틀을 제외 → 솔로랭크는 공백 구간 플레이가 없어 실질 결과 차이는 없다(극소수 경계만). 정확 parity 대신 균일·명확한 의미를 택함.
  • result 매핑: 쿼리는 raw result 문자열로 그룹핑, 앱에서 BattleResult.findByCode 로 매핑하고 미지정은 무시 → accumulator 의 ?: return 과 동일.
  • cache-aside 잔여 레이스: "읽기 재계산 ↔ 쓰기 커밋/무효화"가 겹치는 극히 드문 창에서 일시적 stale 가능. afterCommit 무효화 + TTL 백스톱으로 완화하며 다음 갱신/TTL 에 자가치유. 지연 이중삭제·버전키 등 과설계는 YAGNI 로 보류하고 한계로 문서화.
  • 빈 결과 캐싱: 배틀 없는 시즌은 빈 items 로 캐싱(재계산 회피). 갱신 시 evict 로 정리.
