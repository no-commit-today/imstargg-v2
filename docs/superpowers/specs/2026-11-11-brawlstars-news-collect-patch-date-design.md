# 공식 뉴스 수집·알림과 패치일 등록 설계

- 작성일: 2026-11-11
- 대상: `core/core-batch`(수집 잡, 알림 발송기), `infrastructure/db-core`(엔티티·DDL), `core/core-enum`(글 유형), `core/core-admin`, `imstargg-admin-frontend`, `imstargg-deploy`(CronJob)
- 상태: 설계 확정 (구현 전)
- 관련: 통계를 날짜 기준에서 패치 기준으로 바꾸는 재설계의 첫 번째 스펙이다. 두 번째 스펙(패치 기준 통계 집계와 최근 업데이트 일시)은 이 스펙이 만드는 패치일 목록을 읽는다.

## 1. 배경

통계를 패치 단위로 끊으려면 밸런스 패치가 언제 있었는지 알아야 한다. 브롤스타즈 전투 기록에는 게임 버전이 없어 패치 경계는 날짜로만 정할 수 있고, 그 날짜의 근거는 공식 블로그의 릴리스 노트다.

2026-11-10~11 조사로 확인한 사실이다.

- **사이트 구조**: 공식 블로그(`https://supercell.com/en/games/brawlstars/blog/`)는 정적 사이트다. 페이지 HTML 안의 `__NEXT_DATA__` 스크립트 태그에 그 페이지의 데이터가 JSON 으로 들어 있다. 목록은 `props.pageProps.articles[]`(title, linkUrl, publishDate), 본문은 `props.pageProps.bodyCollection[]` 이다. 브라우저 없이 HTML 한 번으로 읽힌다.
- **목록**: 쪽당 6건, 게시일 내림차순이다. 글은 한 달에 2~3건 올라온다.
- **후속 패치는 기존 글에 붙는다**: 릴리스 노트 글 맨 위에 "Maintenance - 날짜" 블록이 추가된다. 2026-11-11 에도 11월 릴리스 노트에 밸런스 변경 블록이 붙었다(주소 그대로, 19줄 추가·4줄 삭제, 게시일 11-03 → 11-11).
- **글 번호가 없고 주소·게시일·제목이 모두 바뀐다**:
  - 주소: "UPDATE 65: BUFFIES!" 글이 `update65-2` → `-3` → `-5` 로 바뀌었다. 첫 변경 때 본문은 그대로였다.
  - 게시일: 후속 블록이 붙을 때 올라가는 글이 많다. 시각 부분은 사람이 넣은 정각 값이 섞여 있어 패치 시각이 아니다.
  - 제목과 주소가 함께: 2025년 4월 릴리스 노트가 6월에 "(Updated June 12) …" 제목과 새 주소로 다시 올라왔다(웹 아카이브로 확인, 피드 87건 중 1건).
- **제목만으로는 릴리스 노트를 다 가리지 못한다**: "Release Notes"·"Patch Notes" 규칙은 피드 87건 중 18건을 오탐 없이 잡지만, 2025-12 본편 글 "UPDATE 65: BUFFIES!" 와 밸런스 단독 글 2건을 놓친다.
- **글이 삭제되기도 한다**: UPDATE 65 글은 2026년 2~3월 사이에 지워졌다.
- **블로그에 없는 변경도 있다**: 2025-12-03 수치 수정은 공식 X 의 점검 공지뿐이었다.

## 2. 범위

### 만드는 것

- **수집 잡**: 하루 두 번 공식 블로그 목록 3쪽을 읽고, 그 안의 모든 글 본문을 받아 판 단위로 저장한다.
- **알림**: 새로 저장한 판마다 Discord 로 알린다.
- **어드민**: 글 목록과 이력, 판 사이의 변경 비교, 유형 수정, 패치일 등록·수정·삭제.
- **패치일 목록**: 운영자가 어드민에서 등록하는 KST 날짜. 패치 버전으로 쓴다.

### 범위 밖

- 통계 집계와 사용자 화면 (두 번째 스펙)
- 공식 X·네이버 카페 감시, 한국어판 본문
- 목록 3쪽 밖의 글과 피드에 노출되지 않는 글
- 잡 실패 알림 장치를 새로 만드는 일 (core-batch 에 이미 있는 공통 잡 실패 알림을 그대로 쓴다)

## 3. 결정 요약

| 항목 | 결정 |
|---|---|
| 테이블 | 글(한 행 = 한 판), 패치일. 목록 테이블은 두지 않는다. |
| 읽는 범위 | 목록 1~3쪽(글 18건)의 모든 글. 유형과 무관하게 본문을 저장한다. |
| 실행 주기 | 하루 두 번, 09:20 과 21:20 KST |
| 같은 판의 기준 | 주소, 제목, 본문이 모두 같아야 같은 판이다. 게시일은 저장만 하고 비교하지 않는다. |
| 이력 | 주소 키(`article_key`)가 같은 행들이 한 글의 이력이다. |
| 본문 저장 | 원문 JSON 과 줄별 글자만 뽑은 본문을 함께 둔다. 영어판 기준. |
| 본문 비교 | 해시 없이, 글자만 뽑은 본문끼리 직접 비교한다. |
| 유형 | 릴리스 노트·기타. 제목으로 판정하고 다음 판은 직전 판의 유형을 물려받는다. 어드민에서 고친다. |
| 저장과 알림 | 행마다 저장한 뒤 알린다. 재전송 장치는 없다. |
| 오류 | 어디서든 예외는 그대로 던져 잡이 멈춘다. 건너뛰기와 이 잡만의 실패 알림은 두지 않는다. 실패는 공통 잡 실패 알림이 알린다. |
| 알림 발송기 | 전송 실패를 삼키지 않고 던지도록 발송기 자체를 고친다(모든 잡 공통). |
| 패치일 | 글과 독립된 목록. KST 날짜. 등록·수정·삭제는 패치 뒤 30일까지. |

## 4. 데이터 모델

엔티티는 db-core 에 두고 DDL 은 `schema.sql` 과 마이그레이션 파일 양쪽에 멱등하게 쓴다. 외래 키 제약은 걸지 않는다.

### 4.1 글 `brawlstars_news_article`

한 행이 글의 한 판이다. 저장한 행은 `type` 과 `content` 말고는 바꾸지 않는다.

| 컬럼 | 타입 | 내용 |
|---|---|---|
| `brawlstars_news_article_id` | bigint, identity PK | |
| `article_key` | varchar, not null | 주소 키. 같은 값의 행들이 한 글의 이력이다. |
| `link_url` | varchar, not null | 그 판을 받은 주소(절대 주소, 끝 슬래시 없음) |
| `title` | varchar, not null | 그 판의 제목 |
| `published_at` | timestamptz, not null | 그 판을 받았을 때의 게시일. 사이트가 준 값 그대로이고 비교에 쓰지 않는다. |
| `type` | varchar, not null | `RELEASE_NOTE` 또는 `OTHER` |
| `raw_body` | text, not null | 사이트가 준 `bodyCollection` JSON 문자열 그대로 |
| `content` | text, not null | 줄별 글자만 뽑은 본문(6장). `raw_body` 에서 만든 값이다. |
| `created_at`, `updated_at` | timestamptz | 공통 컬럼. `created_at` 이 그 판을 처음 본 시각이다. |

- 유니크와 인덱스를 두지 않는다. 같은 주소의 행이 판마다 생기고, 행은 처음 18건에 연 수십 건이 더해지는 수준이다.
- `raw_body` 는 jsonb 가 아니라 text 다. 받은 그대로 보존하고 테스트 DB(H2)와 어긋나지 않는다.
- 릴리스 노트 한 판은 원문 77~145KB, 글자만 뽑은 본문 31~45KB 다.

### 4.2 주소 값 타입과 주소 키

주소는 임베디드 값 타입 하나로 두고 `link_url` 과 `article_key` 두 컬럼을 맡긴다. 주소 문자열로 만들면 그 안에서 다음을 한다.

1. 목록이 주는 경로(`/en/games/brawlstars/blog/{분류}/{슬러그}`)에 사이트 주소를 붙여 절대 주소로 만들고 끝 슬래시를 뗀다 → `link_url`
2. 마지막 구간(슬러그)을 꺼낸다.
3. 끝이 `-숫자 1~2자리`(정규식 `-\d{1,2}$`)면 한 번 뗀다 → `article_key`

| 주소의 마지막 구간 | `article_key` |
|---|---|
| `update65-2`, `update65-3`, `update65-5` | `update65` |
| `brawl-cup-event-guide-2` | `brawl-cup-event-guide` |
| `release-notes-november-2026` | `release-notes-november-2026` (연도는 남는다) |
| `balance-changes-13-2` | `balance-changes-13` |

- 분류를 키에 넣지 않는다. 사이트 글 272건에서 같은 슬러그가 서로 다른 분류에 있는 경우는 없었고, 글이 다른 분류로 옮겨 다시 올라와도 이력이 이어진다.
- 숫자를 2자리까지만 떼는 것은 연도 때문이다. 릴리스 노트 주소가 `release-notes-{월}-{연도}` 꼴이라, 제한 없이 떼면 같은 달의 릴리스 노트가 해마다 한 글로 묶인다.
- 규칙은 주소에서 바로 계산되므로, 나중에 고치면 저장된 `link_url` 로 `article_key` 를 다시 만들 수 있다.

### 4.3 패치일 `brawlstars_patch`

| 컬럼 | 타입 | 내용 |
|---|---|---|
| `brawlstars_patch_id` | bigint, identity PK | |
| `patch_date` | date, not null, 유니크 | 패치일(KST 날짜)이자 패치 버전 |
| `memo` | varchar, null | 메모 |
| `created_at`, `updated_at` | timestamptz | 공통 컬럼 |

- 글과 연결하지 않는다. 릴리스 노트가 아닌 글이나 글 없는 변경도 같은 방식으로 등록한다.
- 삭제는 행을 지운다.
- 등록 기한 일수(30)는 상수 한 곳에 두고 이 엔티티 가까이에 둔다. 두 번째 스펙은 이 기한 안의 날짜를 원본 전투에서 다시 읽으므로, 원본 전투의 보관 일수(45)가 이 값보다 길어야 한다.

## 5. 수집 흐름

### 5.1 실행

- 잡은 core-batch 의 CronJob 하나다. 스케줄은 `20 0,12 * * *`(UTC), 즉 09:20 과 21:20 KST 다. 지금까지의 패치 점검 9건이 모두 14:47~15:52 KST 에 시작돼, 저녁 실행이면 패치 당일에 알림이 온다.
- 패치 당일은 통계에서 빠지므로 감지가 반나절 늦어도 다음 날 안에 등록하면 통계에 차이가 없다.

### 5.2 한 번의 실행

1. **목록 읽기**: 1쪽(`/en/games/brawlstars/blog/`)과 2·3쪽(`/en/games/brawlstars/blog/page/{N}/`)을 읽는다. 같은 주소가 두 쪽에 나오면 한 번만 다룬다. 읽는 쪽 수(3)는 상수다.
2. **본문 받기**: 글마다 주소 끝에 슬래시를 붙여 요청하고 `bodyCollection` 을 꺼낸다.
3. **글자 뽑기**: 6장의 규칙으로 줄별 글자만 뽑는다.
4. **직전 판 찾기**: 같은 `link_url` 의 가장 최근 행을 먼저 찾는다. 없으면 같은 `article_key` 의 가장 최근 행이다. 가장 최근은 id 가 가장 큰 행이다.
5. **비교**: 직전 판과 주소, 제목, 글자만 뽑은 본문이 모두 같으면 넘어간다.
6. **저장과 알림**: 하나라도 다르거나 직전 판이 없으면 새 행을 저장하고, 이어서 알린다.

직전 판을 주소로 먼저 찾는 이유는 같은 주소 키의 서로 다른 주소 두 건이 목록에 함께 있을 때 때문이다. 주소 키만으로 찾으면 두 글이 서로를 직전 판으로 삼아, 실행마다 "주소 변경"이 번갈아 저장되고 알림이 끝없이 나간다. 주소로 먼저 찾으면 둘 다 자기 행과 비교해 넘어간다.

글은 게시일이 늦은 것부터 처리한다. 예외가 나면 그 자리에서 멈추므로, 옛 글 하나의 실패가 최신 글(특히 최신 릴리스 노트)을 막지 않게 하기 위해서다. 요청은 한 번에 하나씩 차례로 보내고, 요청 사이에 0.1~1초를 무작위로 쉰다(목록과 본문을 구분하지 않는다). 한 번 실행에 요청은 21건이다.

### 5.3 사이트를 읽는 방식

- **클라이언트**: core-batch 안에 전용 HTTP 클라이언트를 둔다. 브롤스타즈 API 용 클라이언트(API 키, 레이트리미터)와 섞지 않는다. 타임아웃은 공통 HTTP 설정(연결 3초, 응답 10초)을 따르고 재시도는 하지 않는다.
- **문자 해석**: 응답을 바이트로 받아 UTF-8 로 직접 해석한다. 사이트가 문자 인코딩을 알려 주지 않는다.
- **응답 검증**: 상태 코드가 200 이고, `__NEXT_DATA__` 가 있고, 목록에는 비어 있지 않은 `articles` 배열이, 글 페이지에는 비어 있지 않은 `bodyCollection` 배열이 있어야 한다. 글 페이지는 `page` 값이 글 경로(`…/blog/[category]/[title]`)인지도 본다. 없는 글의 페이지에도 `__NEXT_DATA__` 가 있어 상태 코드만으로 판단하지 않는다. 하나라도 어긋나면 예외다.

### 5.4 비교와 저장

- **주소·제목**: 받은 값(제목은 앞뒤 공백 제거)을 직전 판의 값과 그대로 비교한다.
- **본문**: 직전 판의 `raw_body` 를 지금 규칙으로 다시 뽑은 글자와, 방금 받은 본문에서 뽑은 글자를 비교한다. 규칙을 고쳐 배포해도 가짜 변경이 생기지 않는다.
- **저장된 본문 맞추기**: 다시 뽑은 글자가 직전 판의 `content` 와 다르면 규칙이 바뀐 것이다. 같은 `article_key` 의 모든 행의 `content` 를 각 행의 `raw_body` 로 다시 만들어 저장한다. 알림은 보내지 않는다.
- **유형**: 직전 판이 있으면 그 유형을 물려받는다. 없으면 제목으로 판정한다. 제목이 정규식 `release notes|patch notes|\bupdate \d+\b`(대소문자 무시)에 맞으면 릴리스 노트, 아니면 기타다. "Update + 숫자"는 "UPDATE 65: BUFFIES!" 한 건을 근거로 넣은 규칙이고, 현재 피드 87건에서 다른 글에는 맞지 않는다.

### 5.5 첫 실행

글 테이블이 비어 있으면 읽은 글 전부를 한 트랜잭션으로 저장한다. 이때만 게시일이 이른 글부터 넣어 id 가 시간순이 되게 한다. 글마다 알리지 않고 요약 알림 1건만 보낸다. 중간에 실패하면 한 건도 남지 않아 다음 실행이 처음부터 다시 한다. 요약 알림은 Discord 설정이 운영에서 제대로 걸렸는지 가동 첫날에 확인하는 용도다.

## 6. 글자 뽑기 규칙

`bodyCollection` 은 블록의 배열이고, 블록마다 제목과 문단·목록의 나무 구조(JSON)가 있다. 여기서 글자만 한 줄씩 뽑는다. 표시(제목 기호, 목록 기호)는 붙이지 않는다.

| 대상 | 처리 |
|---|---|
| 글 블록, 기능 소개 블록 | 블록 제목을 한 줄로 쓰고, 본문을 이어 쓴다. |
| 이미지·영상 블록 | 버린다. |
| 문단, 소제목, 목록 항목 | 각각 한 줄 |
| 표의 행 | 칸을 공백으로 이어 한 줄 |
| 링크, 굵게, 기울임 | 글자만 남긴다. |
| 공백 | 특수 공백은 일반 공백으로 바꾸고, 연속 공백은 한 칸으로 줄이고, 빈 줄은 없앤다. |
| 모르는 종류의 블록 | 버리지 않고 `[?종류]` 한 줄을 남긴다. |

- 예외는 마지막 줄 하나다. 사이트 구조가 바뀌어 글자를 못 뽑는 상황을 조용히 지나치지 않기 위해서다.
- 사이트 글 272건에서 블록 종류는 글, 기능 소개, 이미지, 영상 네 가지뿐이었다.
- 규칙은 실제 글의 구조를 그대로 둔 사본으로 결과를 고정한다(10장).

## 7. 알림

저장한 행마다 알림 1건을 보낸다. 유형과 무관하게 같은 형식이고, 본문은 싣지 않는다. 링크는 공식 글 주소만 넣는다. 기존 Discord 채널을 그대로 쓴다.

| 종류 | 언제 | 담는 것 |
|---|---|---|
| 새 글 | 직전 판이 없는 행을 저장했을 때 | 유형, 제목, 주소, 게시일, 감지 시각 |
| 변경 | 직전 판이 있는 행을 저장했을 때 | 유형, 제목, 주소, 감지 시각, 직전 판을 본 시각, 바뀐 항목 |
| 첫 실행 요약 | 가동 첫 실행 | 저장한 글 수, 릴리스 노트 수, 가장 최근 릴리스 노트의 제목과 주소 |

변경 알림의 모양이다.

```text
[변경] [릴리스 노트] Release Notes November 2026
https://supercell.com/en/games/brawlstars/blog/game-updates/release-notes-november-2026
감지 2026-11-11 21:20 KST · 직전 판 2026-11-10 21:20 KST
게시일 2026-11-03 → 2026-11-11
본문 19줄 추가, 4줄 삭제
```

- 바뀐 것만 적는다. 주소·제목·게시일이 바뀌었으면 "이전 → 새"로, 본문이 그대로면 "본문 동일"로 적는다.
- 줄 수는 두 본문의 줄을 견줘 한쪽에만 있는 줄을 센 것이다.
- 시각은 KST 로 적는다.

## 8. 오류 처리

- **어디서든 예외는 그대로 던진다.** 목록을 못 읽든, 글 하나의 본문을 못 받든, 응답 검증에 걸리든, 저장이 실패하든 잡이 그 자리에서 멈춘다. 특정 건을 건너뛰거나 실패를 모아 두지 않는다.
- **수집 실패를 이 잡에서 따로 알리지 않는다.** 실패한 잡은 core-batch 의 공통 잡 실패 알림이 Discord 로 알린다. 잡 상태와 ERROR 로그도 남는다.
- **다시 실행해도 결과가 같다.** 재시도든 다음 정시 실행이든, 이미 저장한 판은 직전 판으로 읽혀 넘어가고, 저장 전이던 글은 이어서 저장하고 알린다. 실패한 잡을 컨테이너가 바로 다시 띄우는지는 배포 차트의 기본값에 달려 있고 확인하지 않았다.
- **새 잡은 브롤스타즈 API 용 잡 포장을 쓰지 않는다.** 그 포장은 503 응답을 "점검 중"으로 보고 조용히 넘긴다.

### 8.1 알림 발송기 변경

Discord 발송기는 지금 전송 실패를 로그로만 남기고 넘어간다. 이것을 로그를 남긴 뒤 예외를 던지도록 고친다. 상태 코드 오류는 감싸지 않고 받은 예외를 그대로 던진다. 연결 오류는 예외 메시지에 웹훅 주소가 들어가므로 주소를 뺀 예외로 바꿔 던진다. 로그에는 알림 문구 전문을 남겨, 나중에 로그만으로 무엇을 못 보냈는지 찾을 수 있게 한다. 발송기에 타임아웃도 건다. 지금은 타임아웃이 없어 Discord 가 응답을 물고 있으면 잡이 그만큼 멈춘다.

저장한 뒤 알리므로, 알림 전송이 실패하면 그 한 건의 알림은 다시 나가지 않는다. 다시 뜬 실행은 저장된 행을 보고 넘어가기 때문이다. 이 절충은 알고 고른 것이다.

발송기는 공용이라 기존 잡도 전송 실패 시 잡이 실패하게 된다.

| 잡 | 알림 위치 | 전송 실패 시 달라지는 점 |
|---|---|---|
| 피드백 다이제스트 | 알림만 보냄 | 잡이 실패하고, 다시 뜬 실행이 다시 보낸다. |
| 브롤러 동기화 | 알림만 보냄 | 위와 같다. |
| 이벤트 모드 동기화 | 알림만 보냄 | 위와 같다. |
| API 스펙 추적 | 저장한 뒤 알림 | 잡이 실패한다. 이미 저장됐으므로 그 알림은 다시 나가지 않는다. |
| 배틀 이벤트 동기화 | 저장하기 전에 알림 | Discord 가 죽어 있는 동안 이 잡의 저장도 멈춘다. |
| 배틀 이벤트 동기화의 미등록 로테이션 이벤트 알림 스텝 | 알림만 보냄 | 잡이 실패한다. 앞 스텝의 저장은 남는다. |
| 1인 통계 집계 2종 | 알림을 예외 처리로 감쌈 | 달라지지 않는다. 전송 실패는 로그로 남고 잡은 계속된다. |
| 공통 잡 실패 알림 | 실패한 잡을 알림 | 달라지지 않는다. 전송 실패는 로그로만 남긴다. |

- 전송 실패로 잡이 실패하면 공통 잡 실패 알림이 같은 발송기로 한 번 더 보내 본다. 그것도 실패하면 로그만 남는다.
- 배틀 이벤트 동기화가 Discord 장애 동안 멈추는 것은 감수한다. 그사이 날짜의 저장분이 나중에 채워지는지는 확인하지 않았다(11장).
- 브롤러 동기화, 이벤트 모드 동기화, API 스펙 추적은 503 을 "점검 중"으로 넘기는 포장을 쓰고 있어, Discord 가 503 을 돌려주면 실패가 아니라 "점검 중"으로 끝난다. 이번에 고치지 않는다.

## 9. 어드민

### 9.1 API (core-admin)

| 메서드·경로 | 내용 |
|---|---|
| `GET /news-articles` | 글마다 최신 판 1건과 판 수. 본문은 싣지 않는다. |
| `GET /news-articles/{id}` | 한 판의 상세. 글자만 뽑은 본문과 직전 판의 본문을 함께 준다. 직전 판은 수집과 같은 규칙으로 찾는다(그 판보다 앞선 행 중 같은 주소의 가장 최근 행, 없으면 같은 주소 키의 가장 최근 행). |
| `GET /news-articles/{id}/versions` | 같은 글의 모든 판(본문 제외), 시간순 |
| `PUT /news-articles/{id}/type` | 유형 수정. 같은 `article_key` 의 모든 판에 적용한다. |
| `GET /patches` | 패치일 목록, 오늘(KST), 등록할 수 있는 가장 이른 날짜 |
| `POST /patches` | 등록 (패치일, 메모) |
| `PUT /patches/{id}` | 수정 |
| `DELETE /patches/{id}` | 삭제 |

- 목록 조회는 본문 두 컬럼을 읽지 않는다. core-admin 의 DB 응답 대기가 3초다.
- 원문 JSON 은 API 로 내지 않는다.
- 패치일 등록 API 는 통계를 다시 계산하지 않는다.
- 수정은 PUT 을 쓴다. 어드민의 CORS 설정이 PATCH 를 허용하지 않는다.

### 9.2 화면 (admin-frontend)

기존 화면의 방식을 따른다. 목록·등록·삭제는 점검 화면을, 변경 비교는 API 스펙 화면을 본보기로 삼는다.

| 화면 | 하는 일 |
|---|---|
| 글 목록 | 글마다 한 줄. 유형(바로 수정), 제목(공식 글 새 탭), 게시일, 처음 본 시각, 판 수 |
| 글 이력 | 한 글의 판을 시간순으로 보이고, 고른 판을 직전 판과 줄 단위로 비교한다. |
| 패치일 | 목록, 등록, 수정, 삭제 |

### 9.3 패치일 규칙

- **날짜**: KST 날짜다. 화면에 "KST 기준"이라고 적는다. 날짜는 `yyyy-MM-dd` 문자열로 주고받는다.
- **중복**: 같은 날짜는 한 번만 등록된다.
- **등록 기한**: 오늘(KST)에서 패치일까지가 0일 이상 30일 이하일 때만 등록·수정·삭제할 수 있다.
- **수정**: 날짜를 바꿀 때는 옛 날짜와 새 날짜가 모두 기한 안이어야 한다. 메모만 고칠 때는 기한을 보지 않는다.
- **미래 날짜**: 받지 않는다. 예고된 점검이 밀리면 틀린 경계가 남는다.
- **검증**: 화면의 날짜 입력에서 먼저 막고 서버도 거부한다(400). 없는 id 는 404 다.
- **기한 판정**: "오늘, 패치일"을 받는 순수 함수로 두어 경계를 단위 테스트로 고정한다.

### 9.4 패치일 초기값

테이블을 만드는 마이그레이션 SQL 끝에 구현 시점까지 알려진 패치일을 함께 넣는다. 지금은 2026-11-03 과 2026-11-11 이다. 가동이 늦어 30일 기한을 넘겨도 들어가 있게 하기 위해서다. 그 뒤의 패치일은 어드민으로 등록한다.

- 넣는 문장은 다시 실행해도 같은 결과가 되게 쓴다(같은 날짜가 있으면 넘어감).
- `schema.sql` 에는 넣지 않는다. 그 파일에는 데이터 문장이 없다.

## 11. 배포

1. 운영 DB 에 마이그레이션 SQL 을 직접 적용한다(테이블 2개와 패치일 초기값). 새 테이블뿐이라 지금 떠 있는 앱에 영향이 없다.
2. core-batch 를 배포하고 기존 잡이 정상인지 확인한다. 이 배포에는 아직 운영에 나가지 않은 변경(HTTP 클라이언트 교체)이 함께 실린다. 알림 발송기 변경도 이때 모든 잡에 적용된다.
3. 그 뒤에 배포 설정에 새 CronJob 항목을 추가한다. 먼저 추가하면 옛 이미지가 모르는 잡 이름으로 뜬다.
4. 첫 실행에서 글 18건이 저장되고 요약 알림이 오는지 확인한다.

되돌릴 때는 배포 설정에서 잡 항목만 뺀다. 테이블은 남아 있어도 해가 없다. core-admin 과 admin-frontend 는 배포 없이 로컬에서 띄운다.

배포 뒤 확인할 것: 배틀 이벤트 동기화 잡이 알림 전송 실패로 멈춘 적이 있는지, 멈췄다면 그 날짜의 저장분이 다음 실행에서 채워지는지.

## 12. 알려진 한계

- **주소가 통째로 바뀐 재게시**: 이력을 잇지 못하고 새 글로 들어온다. 알림은 "새 글"로 나간다. 관측 1건.
- **번호만 다른 주소의 서로 다른 글**: `balance-changes-18`, `-19` 처럼 같은 이름으로 연재된 글은 한 글의 이력으로 묶인다. 저장과 알림은 정상이고, 뒤에 올라온 글이 처음 저장될 때 "새 글" 대신 "변경"으로 표시된다. 그 뒤로는 주소마다 자기 행과 비교한다. 2019~2021년에 있던 꼴이다.
- **한 글의 실패가 그보다 옛 글을 막는다**: 최신 글부터 처리하고 예외에서 멈추므로, 어떤 글의 본문을 계속 읽지 못하면 그보다 옛 글의 변경은 코드를 고칠 때까지 보지 못한다. 목록 3쪽 중 한 쪽을 못 읽으면 그 실행은 아무 글도 처리하지 않는다.
- **3쪽 밖의 글**: 18번째 뒤로 밀린 글의 수정은 보지 못한다. 지금까지 릴리스 노트가 가장 많이 밀린 자리는 10번째였다.
- **블로그 밖의 변경**: 공식 X 로만 공지된 수정, 업데이트 사이에 풀리는 신규 하이퍼차지는 감지하지 못한다. 운영자가 패치일을 직접 등록한다.
- **게시일만 바뀐 경우**: 새 행을 만들지 않으므로 저장된 게시일이 사이트와 달라질 수 있다.
- **알림 유실**: 저장 뒤 전송이 실패한 알림은 다시 나가지 않는다. 흔적은 ERROR 로그다.
- **Discord 장애 중의 실패**: 수집 실패는 공통 잡 실패 알림으로 온다. Discord 자체가 죽어 있으면 그 알림도 오지 않아, 잡 상태와 로그를 봐야 안다.
- **감지 지연**: 최대 12시간에 사이트 캐시 지연이 더해진다.
- **같은 실행이 겹칠 때**: 정시 실행끼리는 겹치지 않는다. 수동 실행이 겹치면 같은 판이 두 번 저장될 수 있으나 해가 없다.

## 13. 두 번째 스펙으로 넘기는 것
