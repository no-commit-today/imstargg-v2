# 봇 전투 제외 설계 (스펙 C1)

- 작성일: 2026-11-06
- 대상: `core/core-batch`(통계 집계기, 일별 잡의 감시), `imstargg-frontend`(소개 페이지 문구), `imstargg-backend/docs`(통계 데이터 전략 문서). 운영 DB 의 일회성 정리(백업 후 삭제)는 런북으로 적는다.
- 상태: 설계 확정 (구현 전)
- 관련: 스펙 A([2026-11-03-stats-event-mode-whitelist-design.md](2026-11-03-stats-event-mode-whitelist-design.md))와 스펙 B([2026-11-04-combo-stats-redesign-design.md](2026-11-04-combo-stats-redesign-design.md))가 수집 편향과 티어 스코어 산식을 "스펙 C" 로 미뤘다. 스펙 C 를 둘로 나눈다. 이 문서(C1)가 수집 편향의 원인인 봇 전투를 통계에서 빼고, 티어 스코어 산식 재검토(C2)가 뒤따른다. 스펙 A·B 와 `ComboStatsPolicy` KDoc 이 말하는 "스펙 C" 중 수집 편향(스펙 B)은 이 문서를, 산식과 "합산 맥락을 핵심 6모드로 좁힐지"(스펙 A §3.2, 부록 A.5)는 C2 를 가리킨다. C2 의 트로피 티어 평가는 이 스펙이 적용된 데이터로 한다. 부록 이름은 앞 스펙에 이어 "부록 C" 다.

## 1. 배경

스펙 B 는 "트로피전에서 수집 플레이어 팀이 60.9% 이긴다(경쟁전 49.4%)" 는 치우침을 원인 미확인으로 남겼다. 운영 DB(읽기 전용)로 원인을 확인했다. 수치의 출처와 방법은 [부록 C](#부록-c-분석-근거-2026-11-05--06)에 있다. 아래에서 **수집자**는 그 전투를 수집한 전투 기록의 주인(`player_brawlstars_tag`)이다.

- **원인은 매치메이킹 봇이다.** 공식 2026년 2월 릴리스 노트의 매치메이킹 표가 봇 매치를 브롤러 트로피 0~1999 에서 켜고 2000 이상에서 끈다고 적는다. 치우침은 정확히 그 구간에만 있다.
- **3대3**: 수집자 본인이 트로피 1000~1999 인 트로피전 전투의 27 ~ 34% 는 상대 세 명이 봇이다. 그 전투의 수집자 팀 승률은 93 ~ 95% 다. 상대에 "다른 전투의 수집자로 확인된 실제 플레이어" 가 한 명이라도 있으면 수집자 팀 승률은 48 ~ 50% 다.
- **쇼다운**: 봇이 로비 일부를 채운다. 수집자 본인 1000~1999 의 1위 비율이 솔로 42%(기대 10%), 듀오 53%(20%), 트리오 53%(25%)다. 2000 이상에서는 기대값 근처다(10.6%, 21.1%, 26.2%). 모두 10-30 ~ 11-05 합이다.
- **봇의 모양**: 봇의 트로피는 전투마다 "그 전투에 있는 사람들의 평균 트로피 − 25" 근처에 만들어진다. 이름은 약 72% 가 기본값 `Brawler` 이고, 봇 슬롯의 태그는 다른 전투의 수집자로 등장하지 않는다(0.03%, 실제 플레이어는 2 ~ 7%).
- **통계가 틀어져 있다.** `TROPHY_1000_PLUS` 의 진영 승률이 수집자 팀 60.4%, 상대 팀 39.6% 다(10-30 ~ 11-05). 봇이 고르는 브롤러가 몇 개에 몰려 있어(EDGAR 는 실제의 3.7배, MEG 9.6배) 그 브롤러의 승률이 내려간다. 봇 전투를 빼기 전후 브롤러 승률의 순위 상관이 0.79 다. 쇼다운의 브롤러 평균 순위는 전후 순위 상관이 솔로 0.54, 듀오 0.22, 트리오 0.60 이다. 듀오·트리오의 지금 순서는 브롤러가 봇 로비를 얼마나 자주 만났는가와 상관이 크다(순위 상관 0.58, 0.61. 솔로는 0.08).
- **조합·카운터도 같은 전투에서 나온다.** EDGAR+MEG 2인 조합은 등장의 92% 가 상대 팀이고 합산 승률이 13.5% 다.
- **조회 때는 고칠 수 없다.** 집계 테이블에는 진영도 슬롯 정보도 없다. "수집자 팀 슬롯만 세기" 도 답이 아니다. 사람 쪽 승률에 봇 상대 승리가 브롤러마다 다르게(3.5 ~ 13.8pp) 섞인다.
- **봇의 겉모습은 바뀐다.** 봇의 이름·태그 표기는 2026년에만 두 번(04-22, 06-30) 바뀌었고, 2000 이상 수집자에게 붙던 봇 매치는 10-29 17시(한국 시각)에 꺼졌다. 트로피가 사람 평균에 몰리는 모양은 그 변화들을 거치는 동안 그대로였다.

## 3. 설계

### 3.1 판정 규칙 — `StatsBotBattlePolicy` (core-batch `domain/statistics`)

`object StatsBotBattlePolicy` 하나에 상수, 판정 함수 둘(`isBotBattle`, `isBotLobby`), 그 둘을 이루는 단계 함수를 둔다. core-api 의 `ComboStatsPolicy` 와 같은 방식으로 근거와 결정 이력을 KDoc 에 적는다. 모두 순수 함수이고 Spring 에 기대지 않는다. 예외를 던지지 않는다. 조건을 하나라도 만족하지 않으면 `false` 다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `BOT_TROPHY_LIMIT` | 2000 | 봇 슬롯의 트로피 상한(미만). 공식 규칙의 봇 매치 구간 |
| `TEAM_AVERAGE_WINDOW_LOWER` | −75 | 3대3 창의 하한(포함), 수집자 팀 평균 대비 |
| `TEAM_AVERAGE_WINDOW_UPPER` | +25 | 3대3 창의 상한(제외) |
| `CLUSTER_WIDTH` | 75 | 쇼다운 몰림 창의 폭 |
| `SOLO_SHOWDOWN_CLUSTER_THRESHOLD` | 5 | 솔로 쇼다운에서 몰린 팀 수가 이 값 이상이면 봇 로비 |
| `DUO_SHOWDOWN_CLUSTER_THRESHOLD` | 2 | 듀오 쇼다운의 같은 값 |
| `TRIO_SHOWDOWN_CLUSTER_THRESHOLD` | 2 | 트리오 쇼다운의 같은 값 |

| 함수 | 뜻 |
|---|---|
| `appliesTo(battle: StatsResultBattleEntity)` | 3대3 적용 범위(아래 1 ~ 3번) |
| `opponentsBelowBotLimit(battle: StatsResultBattleEntity)` | 3대3 의 4번 |
| `opponentsInTeamAverageWindow(battle: StatsResultBattleEntity)` | 3대3 의 5번. 4번과 무관하게 판정한다 |
| `isBotBattle(battle: StatsResultBattleEntity)` | 위 셋을 모두 만족 |
| `appliesTo(battle: StatsRankBattleEntity)` | 쇼다운 적용 범위(아래 1 ~ 3번) |
| `isBotLobby(battle: StatsRankBattleEntity)` | 적용 범위를 만족하고 몰린 팀 수가 임계값 이상 |

- 반환형은 모두 `Boolean` 이다. 4번·5번 함수는 적용 범위를 만족하지 않는 전투에 `false` 를 돌려준다.
- 단계 함수를 따로 두는 까닭은 §3.3 의 누적기가 "적용 범위 밖" 과 "창은 만족하지만 상대에 2000 이상이 있음" 을 구분해야 하기 때문이다. 누적기가 범위·창 산식을 다시 쓰면 두 산식이 따로 변한다.
- 모드는 `StatsEventMode.find(battle.eventModeBrawlStarsId)` 로 정한다. 원본의 `mode` 문자열은 보지 않는다(모드 45 는 `brawlBall`, 48 은 `siege` 로 온다). 트로피는 팀원의 `brawler.trophies` 다.

**`isBotBattle(battle: StatsResultBattleEntity): Boolean`** 은 아래를 모두 만족할 때 `true` 다. 1 ~ 3 이 적용 범위이고 4 ~ 5 가 판정이다.

1. 전투 유형이 트로피전이다. `battle.type` 은 문자열 코드라 `EnumCodeType.findByCode<BattleType>(battle.type)` 가 `BattleType.RANKED` 인지로 본다(기존 집계기와 같은 방식). 경쟁전(`SOLO_RANKED`), 챌린지, 토너먼트, 알 수 없는 코드는 `false`. 유형을 가장 먼저 본다. 경쟁전 행의 `trophies` 에는 트로피가 아니라 랭크 티어 값이 들어 있다.
2. 모드가 `StatsEventMode` 의 결과형 모드(`resultType` 이 `RESULT`)다. 허용 목록에 없는 모드는 `false`.
3. 팀이 2개이고 각 팀이 3명이다. `playerTeams()` 가 정확히 한 팀이고 `enemyTeams()` 가 정확히 한 팀이다. 여섯 슬롯 중 `brawlStarsTag` 가 `playerBrawlStarsTag` 와 같은 슬롯이 정확히 하나다. 수집자가 어느 팀에도 없거나 두 번 나오면 `false`(측정 기간에는 0건이다).
4. 상대 세 명의 트로피가 모두 2000 미만이다.
5. 수집자 팀 세 명의 트로피 합을 S 라 할 때 상대 세 명 각각의 트로피 t 가 `3·t ≥ S − 225` 이고 `3·t < S + 75` 다.

- 5번은 "t 가 수집자 팀 평균의 −75 이상 +25 미만" 과 같다. 평균을 정수 나눗셈으로 내면 경계에서 측정과 달라지므로 정수 비교식으로 고정한다.
- 수집자 팀을 기준으로 상대 쪽만 본다. 양 팀에 대칭으로 적용하지 않는다([부록 C.2](#c2-3대3-규칙-변형-비교)).
- 2번에서 모드를 보는 까닭은 측정이 허용 모드 9개에서만 이뤄졌기 때문이다. 팀 구성은 엔티티가 보장하지 않으므로 3번에서 정책이 직접 확인한다.

**`isBotLobby(battle: StatsRankBattleEntity): Boolean`** 은 아래를 모두 만족할 때 `true` 다. 1 ~ 3 이 적용 범위이고 4 ~ 6 이 판정이다.

1. 전투 유형이 트로피전이다(3대3 의 1번과 같은 방식).
2. 모드가 `SOLO_SHOWDOWN`(6), `DUO_SHOWDOWN`(9), `TRIO_SHOWDOWN`(38) 중 하나이고, 팀 수와 각 팀의 인원이 그 모드의 `teamCount`·`teamSize`(10×1, 5×2, 4×3)와 같다. 다른 모드와 다른 구성은 `false`.
3. `playerTeams()` 가 정확히 한 팀이고, 전 슬롯 중 `brawlStarsTag` 가 `playerBrawlStarsTag` 와 같은 슬롯이 정확히 하나다.
4. **자격 있는 팀** = `enemyTeams()` 중 팀원 전원의 트로피가 2000 미만인 팀.
5. 자격 있는 팀 A 마다 창 `[min(A), min(A) + 75)` 를 놓는다. 자격 있는 팀 T 는 `min(T) ≥ min(A)` 이고 `max(T) < min(A) + 75` 일 때 그 창에 든다. A 자신에게도 같은 조건을 건다. `max(A) ≥ min(A) + 75` 인 A 는 자기 창에서 세지 않는다. 창마다 드는 팀 수를 세어 가장 큰 값을 **몰린 팀 수**로 한다. 자격 있는 팀이 없으면 0 이다.
6. 몰린 팀 수가 그 모드의 임계값 이상이다.

- `min`·`max` 는 팀원 트로피의 최솟값·최댓값이다. 솔로는 팀원이 한 명이라 둘이 같다.
- 수집자 팀은 세지 않고, 수집자 본인의 트로피는 조건에 넣지 않는다.
- 판정은 행 단위다. 같은 로비를 다른 팀의 수집자가 수집한 행은 판정이 다를 수 있다(경계에 걸린 로비에서만, 행 기준 0.2 ~ 0.4%). 로비 단위로 맞추지 않는다.

### 3.2 집계기 적용 (core-batch)

| 집계기 | 넣는 것 |
|---|---|
| `BrawlerBattleResultStatsAggregator` (1인) | `aggregate()` 진입부에서 `isBotBattle` 이면 건너뜀 |
| `BrawlerEnemyBattleResultStatsAggregator` (카운터) | 같음 |
| `BrawlerPairBattleResultStatsAggregator` (2인) | 같음 |
| `BrawlerTrioBattleResultStatsAggregator` (3인) | 같음 |
| `BrawlerBattleRankStatsAggregator` (순위형) | `aggregate()` 진입부에서 `isBotLobby` 이면 건너뜀 |

- 전투 단위로 뺀다. 봇 전투에 있던 사람 슬롯도 모두 빠진다(2000 이상인 동료 슬롯 포함). 봇을 상대로 한 승리를 통계에 남기지 않기 위해서다.
- 제외는 티어 범위와 무관하다. 집계기는 슬롯의 티어 범위(`StatsTierRange.resolveAll`)를 정하기 전에 전투를 건너뛰므로, 걸린 전투는 어느 티어 행에도 들지 않는다. 티어가 관여하는 것은 다시 집계할 수 없는 과거 집계의 정리(§3.4 의 4번)뿐이다.
- 리더, Task 의 읽기·쓰기 흐름, Writer 는 바꾸지 않는다. 리더가 넘기는 전투 수(`전투: N건` 로그)는 제외 전 값이다.
- 집계기는 Task 안에서 만들어지고 `aggregate` 는 반환값이 없다. 건너뛴 수는 집계기가 세지 않는다. §3.3 의 누적기가 센다.
- 규칙 함수는 한 곳이고 호출 지점이 다섯 곳이다. 하나가 빠지면 화면 간 수치가 어긋나므로 테스트로 고정한다(§5).

### 3.3 감시 (core-batch)

일별 1인 잡 두 개가 집계하면서 같은 전투로 지표를 센다. 원본을 한 번 더 읽지 않는다.

| 잡 | Task | 누적기 |
|---|---|---|
| `brawlerBattleResultStatsJob` | `BrawlerBattleResultStatsTask` | `StatsBotBattleMonitor` (3대3) |
| `brawlerBattleRankStatsJob` | `BrawlerBattleRankStatsTask` | `StatsBotLobbyMonitor` (쇼다운) |

- 누적기는 `domain/statistics` 의 순수 클래스다. Task 가 실행마다 집계기와 함께 하나씩 만든다.
- Task 는 리더 콜백에서 전투마다 `monitor.record(battle)` 과 `aggregator.aggregate(battle)` 을 부른다. 누적기는 정책 함수를 스스로 부른다(집계기와 누적기가 같은 전투를 각각 한 번씩 판정한다). 누적기는 정책의 판정 함수와 단계 함수만 부르고 범위·창 산식을 다시 쓰지 않는다. 적용 범위를 만족하지 않는 전투는 어느 지표에도 세지 않는다. `record` 는 예외를 던지지 않는다.
- 쓰기가 끝난 뒤 Task 가 요약을 로그로 남기고, 경고 조건에 걸린 지표가 있으면 `AlertManager` 로 warn 알림을 한 번 보낸다. 두 Task 의 생성자에 `AlertManager` 가 더해진다.
- 요약과 알림을 만드는 구간은 Task 가 감싸서, 거기서 난 예외는 로그로만 남기고 집계 잡을 실패시키지 않는다. `DiscordAlertManager` 는 전송 실패를 스스로 삼키지만 알림을 만드는 중의 예외는 스텝을 실패시키기 때문이다.
- 조합 잡 세 개에는 감시를 넣지 않는다(주 묶음 단위라 일별 추세가 나오지 않는다).

**3대3 지표**: 대상은 §3.1 `isBotBattle` 의 1 ~ 3 을 만족하는 전투다. 승률은 수집자 기준 `승 / (승 + 패)` 이고 무승부는 뺀다. "결정전" 은 승패가 난 전투다. 수집자 본인 트로피는 수집자 팀에서 `brawlStarsTag` 가 `playerBrawlStarsTag` 와 같은 팀원의 `brawler.trophies` 다. 1000~1999 는 1000 이상 2000 미만이다.

| 지표 | 정의 | 기준선 | 경고 조건 | 뜻 |
|---|---|---|---|---|
| 걸린 전투 승률 | `isBotBattle` 인 전투의 수집자 팀 승률 | 92.7 ~ 95.0% | 90% 미만 (걸린 결정전 1,000건 이상일 때) | 실제 전투를 지우고 있다 |
| 남은 전투 승률 | 수집자 본인 트로피 1000~1999 이고 `isBotBattle` 이 아닌 전투의 수집자 팀 승률 | 51.8 ~ 52.5% (날짜 전체. 새벽 정기 실행 시점에는 52.2 ~ 53.3%) | 55% 초과 (결정전 5,000건 이상일 때) | 봇을 놓치고 있다 |
| 2000 이상 구간 승률 | 5번(창)은 만족하지만 4번을 만족하지 않는(상대 중 2000 이상이 있는) 전투의 수집자 팀 승률 | 56 ~ 61% | 75% 초과 (결정전 300건 이상일 때) | 2000 위에 봇이 생겼다 |
| 걸리는 비중 | 수집자 본인 1000~1999 인 대상 전투(무승부 포함) 중 `isBotBattle` 인 비율 | 26.9 ~ 34.2% (청크별 25 ~ 43%) | 없음 (로그만) | 수집 시점에 따라 크게 움직인다 |
| 기본 이름 비율 | 걸린 전투의 상대 슬롯 중 팀원 `name`(플레이어 이름. `brawler.name` 이 아니다)이 `Brawler` 인 비율 | 약 72% (71.6 ~ 71.9%) | 없음 (로그만) | 떨어지면 봇 표기가 바뀐 것이다 |

**쇼다운 지표**: 대상은 §3.1 `isBotLobby` 의 1 ~ 3 을 만족하는 전투다. 모드별로 센다. 1위 비율은 `battleRank` 가 1 인 전투의 비율이다.

| 지표 | 기준선 (솔로 / 듀오 / 트리오) | 경고 조건 | 뜻 |
|---|---|---|---|
| 걸린 전투의 1위 비율 | 56.5 ~ 61.8% / 76.3 ~ 81.2% / 76.0 ~ 85.8% | 50% / 70% / 70% 미만 (걸린 전투 1,000 / 500 / 300건 이상일 때) | 실제 로비를 지우고 있다 |
| 남은 전투의 1위 비율 | 9.4 ~ 10.8% / 18.7 ~ 21.6% / 23.5 ~ 28.0% | 12.5% / 24% / 31% 초과 (남은 전투 3,000 / 1,000 / 1,000건 이상일 때) | 봇을 놓치고 있다 |
| 걸리는 비중 | 50.5 ~ 68.7% / 42.1 ~ 62.7% / 38.3 ~ 60.2% | 없음 (로그만) | 날짜에 따라 솔로 18%p, 듀오 21%p, 트리오 22%p 까지 움직인다 |

- 문턱과 최소 표본은 누적기의 상수로 두고 KDoc 에 기준선을 적는다. 기준선은 [부록 C.4](#c4-감시-기준선)의 아홉 날짜를 11-06 에 파티션 전체로 잰 값이다. 3대3 기준선은 창(5번)만 건 값인데, 4번까지 걸어도 0.1%p 안에서만 달라진다.
- 최소 표본에 못 미친 지표는 그날 경고를 판정하지 않고, 요약 로그에 값과 표본 수를 "표본 부족" 으로 남긴다. 트리오의 남은 전투는 기준선 아홉 날짜 중 이틀이 1,000건 미만이다(10-28 468건, 10-29 846건). 전투가 적은 날에는 트리오의 "봇을 놓치고 있다" 판정이 건너뛰어진다.
- 일별 잡은 다음 날 새벽에 그 시점까지 적재된 전투만 본다. 먼저 수집된 전투의 값은 날짜 전체와 조금 다르다.
  - 걸리는 비중은 낮게 나온다.
  - 3대3 의 걸린 전투 승률은 한쪽으로 움직이지 않는다(청크별 92.4 ~ 95.8%). 남은 전투 승률은 대체로 높게 나온다(날짜별 첫 청크 52.2 ~ 53.3%).
  - 쇼다운의 남은 전투 1위 비율도 조금 높게 나온다(11-05 첫 두 청크: 솔로 10.96%, 듀오 21.83%, 트리오 28.11%). 기준선 최댓값을 1%p 안에서 넘을 수 있다.
  - 경고 문턱은 이 폭 밖에 있다.
- 남은 전투의 1위 비율은 수집자 트로피 구성에 따라 조금 움직인다(솔로 본인 1000~1099 는 8.6%, 1900~1999 는 11.2%). 문턱은 그 폭을 감안한 값이다.
- 요약 로그는 잡마다 한 줄이다. 잡 이름은 Task 의 기존 `JOB_NAME` 상수를 쓴다.
  - 3대3: `[잡 이름] 봇 감시 - date, 대상 전투 수, 걸린 전투 수, 본인 1000~1999 전투 수와 그중 걸린 수·비중, 지표 값들`.
  - 쇼다운: `[잡 이름] 봇 감시 - date, 모드별 대상 전투 수, 걸린 수와 비중, 지표 값들`.
  - 3대3 의 "걸린 전투 수 ÷ 대상 전투 수"(20 ~ 27%)는 기준선(26.9 ~ 34.2%)과 분모가 달라 비중으로 찍지 않는다.
- 알림 제목은 `[잡 이름] 봇 전투 규칙 이상 감지` 이고(기존 알림의 "[잡 이름] 무엇 감지" 관례), `AlertCommand.builder().warn()` 으로 만든다. 본문에는 `date` 와 걸린 지표만 한 줄씩(지표, 값, 문턱, 표본 수) 적는다. Discord 본문 한도(2,000자) 안에 들게 하고 나머지는 로그에 둔다.
- 수동 재집계(§3.4)에서도 같은 감시가 돈다.

### 3.4 전환 — 재집계와 과거 집계 정리 (런북)

스키마 변경이 없다. 백엔드 배포는 core-batch 이미지 하나다.

**전제**

- 스펙 A·B 가 운영에 먼저 적용돼 있어야 한다(같은 릴리즈여도 된다). 2026-11-06 기준 운영은 스펙 B 적용 전이다. `brawler_trio_battle_result_stats` 가 없고 2인·카운터 테이블이 예전 구조다([부록 C.6](#c6-운영-테이블-규모-2026-11-06)). 같은 릴리즈로 나가면 스펙 B §3.8 의 ① ~ ⑤(⑤ 는 3인 잡 수동 실행)를 끝낸 뒤 아래 2번·3번을 한다(1번 배포는 스펙 B 의 배포로 끝난 상태다). 4번은 스펙 B ⑥ 의 legacy 대조(`V261104a` 끝의 검증 (a)·(b))를 끝낸 뒤에 한다. 대조를 3번 뒤에 하면 시작일이 W0 보다 이른 묶음만 견준다. 3번이 다시 쓴 묶음(시작일이 W0 이상인 묶음 전부)은 봇 제외로 legacy 와 달라지는 것이 정상이다. 4번이 스펙 B 가 이관한 묶음의 트로피 티어 행을 지우므로 그 뒤에는 시작일이 W0 보다 이른 묶음도 legacy 와 맞지 않는다(경쟁전 티어 행은 그대로다). ⑥ 의 나머지 확인은 기다리지 않는다.
- 아래에서 **T** 는 재집계를 실행하는 한국 날짜다. 수동 실행과 SQL 은 통계 배치 시간대(02:00 ~ 09:00 KST) 밖에서 한다. 같은 날짜·묶음을 두 프로세스가 쓰지 않게 한다.
- **원본이 남는 범위**: `partitionManageJob` 이 T 의 02:00 KST 에 `battle_date < T − 10` 인 일 파티션을 지운다. 그 뒤 남는 원본은 `battle_date ≥ T − 10` 이다. T − 10 파티션은 T + 1 의 02:00 에 지워진다. 그래서 T 에 다시 집계할 수 있는 날짜는 T − 10 ~ T − 1 이고(T 당일은 수집 중이다), 재집계는 T + 1 의 02:00 전에 끝낸다.
- **실행 인자**: `java -jar core-batch.jar --job.name=<잡 이름> date=YYYY-MM-DD rerun=1` 이다(전략 문서 10장). 같은 잡과 `date` 가 이미 완료 상태면 `key=value` 꼴의 인자를 하나 더 붙여야 새로 실행된다(`rerun=1`. 같은 날짜를 또 돌리면 값을 바꾼다). `-Dkey=value` 는 잡 파라미터가 아니다. 쿠버네티스에서 일회성 Job 으로 띄우는 절차는 저장소에 없다. 실행 방법은 운영자가 정하고, 이 스펙은 잡 이름과 인자만 고정한다.

**순서**

1. **배포**: core-batch 를 배포하고 CronJob 이 새 이미지 태그로 바뀌었는지 확인한다. 이후 정기 실행은 새 규칙으로 집계한다. 프론트(§3.5 의 소개 문구)는 같은 릴리즈로 배포하고 아래 순서와 무관하다.
2. **1인 재집계**: `date` = T − 10 ~ T − 1 의 열 날짜를 가장 오래된 날짜부터 `brawlerBattleResultStatsJob` 과 `brawlerBattleRankStatsJob` 으로 실행한다. 두 잡은 그 날짜의 집계 행을 전 티어 통째로 지우고 다시 쓴다.
   - 시작하기 전에 비교할 날짜 하루(T − 10 ~ T − 1 중 하나)의 `TROPHY_1000_PLUS` 를 브롤러별로 떠 둔다(읽기 전용. §5 배포 후 검증의 "재집계 전 값" 이다. 재집계하면 이전 값은 어디에도 남지 않는다): `select brawler_brawlstars_id, sum(victory_count), sum(defeat_count), sum(total_count) from brawler_battle_result_stats where tier_range = 'TROPHY_1000_PLUS' and battle_date = date '<날짜>' group by brawler_brawlstars_id;`
   - 원본이 없는 날짜로 실행하면 그 날짜의 집계가 전 티어에서 지워진다. 범위 밖 날짜를 넘기지 않는다.
   - 재집계는 처음 집계한 뒤에 들어온 늦은 전투도 함께 집계한다. 표본 수는 봇 제외로 줄고 늦은 전투로 는다. 전후 비교에는 두 효과가 섞인다.
   - **D0** = 그 날짜부터 T − 1 까지 두 잡이 모두 성공한 가장 이른 날짜.
3. **조합 재집계**: 카운터·2인·3인 잡은 주 묶음(월 ~ 일, 달 경계에서 자름)을 전 티어 통째로 지우고 다시 쓴다. `date` 가 속한 묶음 하나를 다시 쓰고, `date` 가 그 묶음의 첫날(월요일 또는 1일)이면 직전 묶음도 함께 다시 쓴다.
   - 다시 쓸 수 있는 묶음은 시작일이 T − 10 이상인 묶음뿐이다. 그보다 이른 묶음은 원본이 모자라 부분 데이터로 덮어쓰게 된다.
   - 스펙 B 의 재실행 금지 범위(지난달 1일 ~ 배포일 − 7일. `V261104a` 머리말과 전략 문서 10장)는 이관 묶음을 부분 원본으로 덮어쓰지 않게 하려고 날짜로 적은 근사다. 이 런북은 "다시 쓰는 묶음의 시작일이 T − 10 이상" 을 기준으로 하고, 이를 만족하는 `date` 는 그 금지 범위 안이어도 실행한다. 이관 묶음을 온전한 원본으로 다시 쓰는 것이다.
   - 묶음 하나만 다시 쓰려면 `date` 로 그 묶음의 마지막 날을 넘긴다. 하루짜리 묶음(달 경계)은 다음 묶음의 첫날을 넘겨 두 묶음을 함께 다시 쓴다. 묶음의 첫날을 넘기면 직전 묶음까지 다시 쓰므로, 직전 묶음의 시작일이 T − 10 보다 이르면 넘기지 않는다.
   - 정기 실행(`date` = 전날)은 배포 뒤부터 전날이 속한 묶음을 새 규칙으로 다시 쓴다. 배포가 T 의 새벽 정기 실행(카운터 04:00, 3인 05:00, 2인 07:00 KST)보다 늦었으면 T − 1 이 속한 묶음은 그날 새벽 구 이미지가 쓴 봇 포함 값이다. 세 잡을 `date` = T − 1 로도 실행해 다시 쓴다(T − 1 이 묶음 첫날이면 직전 묶음도 함께 쓰이는데 그 시작일은 T − 8 이상이라 원본이 온전하다).
   - **W0** = 그 묶음부터 지금까지의 모든 묶음을 세 잡이 모두 새 규칙으로 온전히 다시 쓴, 가장 이른 묶음의 `start_battle_date`.
   - 예: 2026-11 초의 묶음은 [10-26 ~ 10-31], [11-01 ~ 11-01], [11-02 ~ 11-08] 이다. T 가 11-09 ~ 11-11 이면 `date=2026-11-02` 로 [11-01 ~ 11-01] 과 [11-02 ~ 11-08] 을 다시 쓴다. T 가 11-10·11-11 이면 `date` = T − 1 로 [11-09 ~ 11-15] 도 다시 쓴다. W0 는 11-01 이다. `date=2026-11-01` 은 넘기지 않는다([10-26 ~ 10-31] 까지 다시 쓰는데 그 앞쪽 원본이 없다). T 가 11-12 면 11-01 원본이 없으므로 `date=2026-11-08` 로 [11-02 ~ 11-08] 을, `date=2026-11-11` 로 [11-09 ~ 11-15] 를 다시 쓴다. W0 는 11-02 다.
4. **백업 후 삭제**: 다섯 집계 테이블에서 다시 집계하지 못한 날짜·묶음의 트로피 티어 행(`TROPHY_1000_PLUS`, `TROPHY_2000_PLUS`, `TROPHY_3000_PLUS`)을 백업 테이블로 옮긴다. 운영 DB 쓰기이므로 사용자가 직접 실행한다. 2 ~ 3번이 끝난 뒤에 하고, 테이블마다 따로 커밋한다.

   | 테이블 | 날짜 컬럼 | 기준 |
   |---|---|---|
   | `brawler_battle_result_stats` | `battle_date` | D0 |
   | `brawler_battle_rank_stats` | `battle_date` | D0 |
   | `brawler_enemy_battle_result_stats` | `start_battle_date` | W0 |
   | `brawler_pair_battle_result_stats` | `start_battle_date` | W0 |
   | `brawler_trio_battle_result_stats` | `start_battle_date` | W0 |

   ```sql
   -- 사전 확인 0 (읽기 전용): 스펙 B 적용 여부. 두 값이 모두 true 가 아니면 멈춘다
   select to_regclass('brawler_trio_battle_result_stats') is not null as trio_exists,
          not exists (
              select 1 from information_schema.columns
              where table_schema = current_schema()
                and table_name in ('brawler_pair_battle_result_stats', 'brawler_enemy_battle_result_stats')
                and column_name = 'event_brawlstars_id'
          ) as combo_migrated;

   -- 사전 확인 (읽기 전용): 옮길 행 수
   select count(*) from brawler_battle_result_stats
   where tier_range in ('TROPHY_1000_PLUS', 'TROPHY_2000_PLUS', 'TROPHY_3000_PLUS')
     and battle_date < date '<D0>';

   -- 옮기기: 지운 행을 한 문장 안에서 그대로 백업 테이블에 넣는다
   set lock_timeout = '3s';
   begin;
   create table brawler_battle_result_stats_backup_<yymmdd>
       (like brawler_battle_result_stats);
   with moved as (
       delete from brawler_battle_result_stats
       where tier_range in ('TROPHY_1000_PLUS', 'TROPHY_2000_PLUS', 'TROPHY_3000_PLUS')
         and battle_date < date '<D0>'
       returning *
   )
   insert into brawler_battle_result_stats_backup_<yymmdd>
   select * from moved;
   -- "INSERT 0 n" 의 n 이 사전 확인한 행 수와 같으면
   commit;
   ```

   - 다른 네 테이블도 같은 꼴이다. 표의 날짜 컬럼과 기준을 넣는다. `<D0>`, `<W0>`, `<yymmdd>`(실행 날짜)는 실행할 때 리터럴로 채운다. 백업 테이블 이름은 `V261103` 의 `…_backup_{yyMMdd}` 관례다.
   - **실행 방식**: psql 대화형 세션에서 한 문장씩 실행한다. 붙여 넣거나 `-f` 로 돌리면 "INSERT 0 n" 의 n 을 확인하기 전에 `commit` 이 실행된다. n 이 사전 확인한 행 수와 다르면 `commit` 대신 `rollback` 한다.
   - 지운 행이 한 문장 안에서 백업으로 들어가므로 백업과 삭제의 건수가 어긋날 수 없다. 다시 실행하면 `create table` 이 실패해 아무것도 바뀌지 않는다. 커밋한 뒤 사전 확인 쿼리를 다시 실행하면 0 이 나온다.
   - **규모**: 1인 결과형은 약 109만 행 중 최대 약 52만 행이 대상이다(트로피 티어 세 개의 행 비중 합 47.8%. D0 이후 날짜의 행은 남는다). 1인 순위형은 약 7.4만 행 중 D0 이전 날짜의 행 전부가 대상이다. 이 테이블에는 트로피 티어 행만 있다([부록 C.6](#c6-운영-테이블-규모-2026-11-06)). 두 테이블의 인덱스는 이벤트·브롤러 ID 로 시작해 이 조건은 순차 스캔이지만 이 크기에서는 문제되지 않는다. 지운 자리는 자동 vacuum 이 다시 쓸 수 있게 만든다. 테이블을 잠그는 `vacuum full` 은 하지 않는다. 조합 테이블은 스펙 B 적용 뒤 묶음당 수만 ~ 수십만 행이고 지난달 1일 이후 묶음만 있다. 실행 전 `explain` 으로 계획을 본다.
   - **지우는 범위**: 트로피 티어 세 개(`TROPHY_1000_PLUS`, `TROPHY_2000_PLUS`, `TROPHY_3000_PLUS`)다. 집계 행에서는 봇 전투만 골라 뺄 수 없어, 봇 전투가 들었을 수 있는 행을 통째로 옮긴다.
     - 티어 범위는 겹쳐 센다. 슬롯의 트로피가 1000 이상이면 `TROPHY_1000_PLUS` 에, 2000 이상이면 `TROPHY_2000_PLUS` 에도, 3000 이상이면 `TROPHY_3000_PLUS` 에도 든다(`StatsTierRange.resolveAll`).
     - `TROPHY_1000_PLUS` 에는 봇 슬롯과 봇 전투의 사람 슬롯이 모두 든다.
     - `TROPHY_2000_PLUS`·`TROPHY_3000_PLUS` 에는 봇 슬롯(2000 미만)이 들지 않지만, 봇 전투에서 이긴 수집자 팀의 2000 이상 슬롯이 든다. 10-29 까지의 날짜에는 수집자 본인 2000~2999 전투의 5.5 ~ 8.9% 가 규칙에 걸리는 봇 전투였다(10-28, 10-29. 승률 97.5 ~ 97.6%). 10-27 이전의 날짜와 본인 3000 이상은 재지 않았다.
     - 10-30 이후의 날짜와 쇼다운은 2000 이상 티어에 든 봇 전투가 적다. 3대3 은 10-30 ~ 11-05 에 규칙에 걸린 440,876 전투 중 수집자 팀에 2000 이상이 낀 것이 642건(0.15%)이고, 쇼다운은 10-28 에도 본인 2000 이상에서 걸리는 로비가 1% 미만이다. 그래도 같은 기준으로 지운다(결정 7). 1인 결과형에서 "10-30 이후인데 다시 집계하지 못한 날짜"(10-30 ~ D0 − 1)는 D0 가 10-31 이후일 때만 생긴다. 2번의 재집계가 모두 성공하면(D0 = T − 10) T 가 11-10 이후일 때다. 카운터·2인·3인은 묶음 단위라 다르다. [10-26 ~ 10-31] 묶음은 T 가 11-06 이후면 시작일이 T − 10 보다 일러 다시 쓰지 못한다. 테이블에 그 묶음이 있으면 10-30·10-31 분이 10-26 ~ 10-29 분과 함께 지워진다. [11-01 ~ 11-01] 묶음은 T 가 11-12 이후면 지워진다(W0 가 11-02 다).
     - 2000 이상 티어만 10-29 까지로 좁혀 지우는 안은 택하지 않았다. 티어마다 기준 날짜가 달라지고 봇 전투가 조금 남는다.
     - 경쟁전 티어(`SOLO_RANK_MYTHIC_PLUS`, `SOLO_RANK_LEGENDARY_PLUS`, `SOLO_RANK_MASTER_PLUS`)의 행은 지우지 않는다. 규칙이 트로피전만 보고, 경쟁전 통계에는 치우침이 없다(수집자 팀 승률 49.4%, 스펙 B).
     - 화면에서는 트로피 티어 세 개 모두 D0·W0 이전 기간의 통계가 없다. 경쟁전 티어는 그대로다. 조회 기간이 통째로 그 기간일 때의 표시는 §3.5 에 적었다.
   - 백업 테이블은 일반 테이블이라 파티션 정리 대상이 아니다. 지운 날짜가 모두 조회 범위 밖으로 나간 뒤(D0 가 속한 달의 다다음 달 1일 이후)에 `drop table` 한다. 복원은 `insert into <원 테이블> select * from <백업 테이블> on conflict do nothing` 이다. 조합 세 테이블은 월 파티션이고 기본 파티션이 없어, 백업 행의 달 파티션이 이미 지워졌으면 문장 전체가 실패한다. 조합 세 테이블의 복원에는 `where start_battle_date >= date '<복원하는 날 기준 지난달 1일>'` 을 붙인다. 그보다 이른 달은 조회 범위 밖이라 복원할 필요가 없다.
   - 이 SQL 은 운영에서 실행해 보지 않았다. 로컬 PostgreSQL 18.3(docker)에서 일반 테이블 둘과 파티션 테이블 셋으로 확인했다(2026-11-07): 건수 대조, 재실행 실패, 복원, 지워진 달 파티션에서의 복원 실패와 `where` 조건. 확인한 항목의 결과는 모두 이 절의 설명과 같았다.
5. **확인**: 통계 캐시(TTL 30분)가 만료된 뒤 화면을 본다. 재집계 실행과 다음 날 새벽 정기 실행의 감시 로그에서 경고가 없는지, 값이 §3.3 의 기준선 근처인지 본다(정기 실행의 값은 §3.3 에 적은 만큼 기준선을 조금 넘을 수 있다). 조합 화면은 T − 1 이 속한 묶음까지 새 규칙으로 쓰인 뒤에 본다.

- **요일**: 월 ~ 목에 재집계한다. 지난주 묶음의 시작일이 T − 10 이상이라 지난주 묶음까지 온전히 다시 쓸 수 있고, 기본 조회 기간(지난주부터)이 재집계 범위 안에 든다. 금 ~ 일에 하면 지난주 묶음과 지난주 앞쪽 며칠의 트로피 티어 통계가 빈다.
- **롤백**: 봇 제외를 되돌린 이미지를 배포한 뒤, 롤백을 실행하는 한국 날짜 T′ 를 기준으로 2번·3번의 범위 규칙을 다시 적용한다.
  - 1인 잡은 T′ − 10 ~ T′ − 1 날짜만, 조합 잡은 시작일이 T′ − 10 이상인 묶음만 다시 집계한다. 그보다 이른 날짜·묶음은 다시 돌리지 않는다. 돌리면 1인은 그 날짜가 전 티어에서 지워지고 조합은 부분 데이터나 빈 값으로 덮인다. 백업에는 트로피 티어의 D0·W0 이전 행만 있어 되살릴 수 없다.
  - 다시 돌리지 못한 구간은 봇 제외 값으로 남는다. 전 구간을 봇 포함 값으로 되돌릴 수 있는 것은 T + 1 의 02:00 전까지다.
  - 옮긴 행은 백업 테이블에서 되살린다(봇 포함 값).
  - 스펙 B 와 같은 릴리즈로 나갔으면 직전 core-batch 이미지는 스펙 B 이전 것이다. `V261104a` 적용 뒤에는 그 이미지의 카운터·2인 잡이 새 테이블에서 실패하고 3인 잡이 없다. 이미지 태그를 되돌리는 방식은 쓸 수 없고, 봇 제외 변경만 되돌린 core-batch 를 새로 빌드해 배포한다. 스펙 B 까지 되돌릴 때만 `V261104a` 머리말의 롤백 절차를 따른다.

**빈 기간의 표시 (바꾸지 않는다)**

- 결정 7 로 트로피 티어 세 개의 D0 이전 기간이 빈다. 조회 기간이 통째로 D0 이전이면 0건이다. D0 가 T − 10 일 때 `LAST_MONTH` 는 T 가 11-11 이후면 2026-12-01 전까지, `TWO_WEEKS_AGO` 는 목요일에 재집계하면 그 주 일요일까지 0건이다. 기본 기간(`SINCE_LAST_WEEK`)을 포함해 오늘까지 이어지는 기간은 0건이 되지 않는다.
- 0건일 때 `/brawlers` 브롤러 탭(`app/brawlers/_components/BrawlerStatTable.tsx`)은 브롤러 목록 기준으로 행을 그린다(`app/brawlers/page.tsx` 의 `toBrawlerRows`). 전 브롤러가 티어 D, 승률·픽률·스타플레이어 비율 0.0%, 전투수 0 이고 1 ~ 3위 행에는 금·은·동 표시가 붙는다. 머리말은 "전체 전투 표본: 0" 이다. 빈 상태 문구("해당 조건에 데이터가 없습니다.")는 검색 결과가 없을 때만 나온다.
- 이 표시는 바꾸지 않는다(결정 10). 전투 표본이 0 이면 빈 상태 문구를 그리는 안은 택하지 않았다. 빈 기간은 두 달 안에 채워지고 기본 기간에서는 생기지 않는다. 릴리즈 노트에 적는다(§6).
- 다른 표는 이미 빈 상태 문구를 그린다(이벤트 상세의 결과형·순위형 표, 브롤러 상세의 일별 차트와 2인·3인·카운터 표, `/brawlers` 의 조합 탭). core-api 는 0건에서 `totalBattleCount` 0 과 빈 목록을 돌려주고 예외를 던지지 않는다.

## 4. 바꾸지 않는 것 (비목표)

- **워커 수집과 원본 스키마.** 봇 전투도 지금처럼 저장한다. 규칙이 몇 달 동안 안정적이면 워커에서 같은 판정으로 저장을 생략할 수 있다. 그때 정책 객체를 공용 모듈로 옮긴다.
- **API 응답 형태와 티어 스코어 산식.** 산식은 스펙 C2 에서 다룬다.
- **순위형 응답의 최소 표본 기준.** 쇼다운 표본이 절반으로 줄어 얇은 브롤러의 평균 순위가 더 흔들린다. 후속 과제로 남긴다.
- **봇이 일부만 낀 전투.** 3대3 에서 봇이 양 팀에 섞인 전투(수집자 본인 1000~1999 전투의 약 2%, 이름 기준 하한. [부록 C.2](#c2-3대3-규칙-변형-비교)), 쇼다운에서 봇이 임계값보다 적게 낀 로비(솔로는 봇 4명 이하, 듀오·트리오는 봇 팀 하나)는 남는다.
- **경쟁전 티어(`SOLO_RANK_…`)의 집계.** 규칙의 대상이 아니고 과거 집계도 지우지 않는다.
- **통계가 0건일 때의 `/brawlers` 브롤러 탭 표시.** 전 브롤러가 티어 D·승률 0.0% 로 그려진다(§3.5).
- **프로필 화면의 개인 전투 기록과 개인 통계.**
- **늦게 들어온 전투가 1인 통계에서 빠지는 문제.** 스펙 B 의 비목표 그대로다.
- **수집 허용 목록 밖 모드의 기존 행.** 스펙 A 가 배포되면 더 쌓이지 않는다. 11-05 부터 쌓인 20인 솔로·10팀 듀오 모드의 행은 판정 대상이 아니다.
- **같은 쇼다운 로비가 여러 수집자 행으로 집계에 여러 번 들어가는 구조.**
- **이용약관(`app/terms/page.tsx`)의 데이터 문단.**

## 부록 C: 분석 근거 (2026-11-05 ~ 06)

운영 DB 읽기 전용 조회다. 원본 `stats_result_battle`·`stats_rank_battle` 의 일 파티션을 `battle_date` 와 id 범위로 잘라 SQL 에서 집계한 수만 받았다. **청크**는 한 날짜 파티션을 id 순(수집 순)으로 나눈 조각이다. 3대3 은 허용 모드 9개의 `ranked` 2팀×3명 전투, 쇼다운은 모드 6·9·38 이다. 승률은 `승 / (승 + 패)` 다. 모든 수치는 독립 검증(다른 작성자가 새로 쓴 SQL 로 다른 날짜를 재조회, 집계 결과의 재계산)을 거쳤다. 분석 원자료(쿼리, 집계 CSV, 검증 기록)는 작업 폴더의 `.superpowers/analysis/` 에 있고 git 에는 남지 않는다. 아래 표가 결정의 근거로 남는 사본이다.

### C.2 3대3 규칙 변형 비교

10-30 ~ 11-05 합계(수집자 본인 1000~1999 약 148만 전투). 오탐 지표는 "확인된 실제 상대가 있는 전투 중 걸린 비율" 이다. 이 열만 확인 표지를 붙인 13개 청크(10-31 ~ 11-02 전체와 11-03 의 청크 1 ~ 4)의 48,764 전투로 쟀고, 확인 기준은 11-01 파티션의 수집자다(11-01 의 세 청크에서는 같은 날짜 파티션이라 C.1 의 "다른 날짜 파티션" 과 다르다). 표 아래의 "약 95% 가 봇", "약 31% 가 실제 전투" 도 같은 13개 청크의 확인 비율로 추정한 값이다.

### C.5 외부 근거

- **공식 2026년 2월 릴리스 노트**의 매치메이킹 변경 표: 봇 매치는 브롤러 트로피 0~999 와 1000~1999 에서 켜져 있고 2000~2999 와 3000 이상에서 꺼져 있다. 3월 4일 점검 항목은 일부러 지면 봇 매치가 잡히던 악용을 고쳤다고 적는다. <https://supercell.com/en/games/brawlstars/blog/release-notes/release-notes-february-2026/>
- **봇 표기의 변화**(공개된 battlelog 덤프 두 곳을 재집계한 결과, 공식 언급 없음): 2026-04-21 까지 실제 계정의 이름·태그, 04-22 ~ 06-29 존재하지 않는 짧은 태그, 06-30 이후 이름 `Brawler` 인 빈 계정(트로피 0, 보유 브롤러 1개, 전투 기록 없음). 한 팀 봇끼리의 트로피 차 중앙값은 6월 이전 24, 이후 16 이고 일반 상대는 517 이다.
- **봇 매치 상한의 이력**: 500 → 600(2023-02-28) → 800(2024-10-29) → 2000(2026-02-25)이라는 것은 위키 변경 이력 기준이고 직접 확인하지 못했다.
- **다른 통계 사이트**: brawltime.ninja(포크 코드)는 상대 봇을 거르지 않고 기록 주인 본인 행만 쓴다. 공식 API 응답에는 봇 표시 필드가 없다.

### C.7 한계

- 그 슬롯이 봇이라는 것을 공식 API 로 직접 확인하지는 않았다. 근거는 서로 독립인 간접 신호다: 수집자로 등장하지 않음, 진영 비대칭, 전투마다 사람 평균에 맞춰 바뀌는 트로피, 승률·1위 비율, 공식 규칙의 구간. `develop` 의 `BATTLE_LOG_UNAVAILABLE` 표시가 운영에 배포되면 직접 잴 수 있다.
- 측정 기간은 2026-10-28 ~ 11-06 의 열흘이다. 시즌 전환·트로피 초기화가 낀 기간은 보지 못했다.
- 재현율은 재지 못했다. 이름 `Brawler` 를 대리 지표로 본 하한만 있다.
- 감시 문턱의 기준선은 아홉 날짜다. 알림이 잦으면 문턱을 다시 잡는다.
- 저장된 전투 기준의 수치다. 워커는 전 참가자가 트로피 1000 이상이고 브롤러가 겹치지 않는 전투만 저장한다. 봇 트로피는 사람 평균보다 낮아 평균이 1000 근처인 봇 전투는 저장되지 않는다.
